AndeSim on FastSim

AndeSim runs its three modes by launching processes and passing a file between them. FastSim already owns the mechanism that replaces all of it: one set of modules, one address map, and a Lua file per platform. This is what the port means, what it deletes, and the order to do it in.

Read from source, 2026-09-11 · andesim · fastsim · vsim_andesim

The goal

All three AndeSim modes — fast, cycle, hybrid — run on FastSim's existing mechanism: greenlib's ModuleFactory, a Lua platform file, and CCI parameters.
The devices are shared because there is only one set of them. Not two implementations kept in step — one router, one gs_memory, one SimControl, reached by whichever CPU is running.
The user-facing behaviour does not change. andesim run --mode hybrid kernel.c still prints one cycle count.

What changes shape

A mode is a platform, and FastSim already expresses a platform as a file. So the three modes stop being three process recipes and become three .lua files selecting from one module set.

What the port deletes

This is the part worth naming plainly: most of what makes AndeSim's driver complicated exists only because the legs are separate processes. FastSim's mechanism does not need any of it. Of 7,883 production lines in driver/, these 2,054 go away — removed, not rewritten.

What stays

The CLI. run, profile, list, doctor and 28 options. Something has to translate them into Lua and CCI parameters — that translator is new code, and it is the price of keeping the user experience unchanged.
The measurement logic. elf_syms.cpp resolves markers to PCs, state_diff.cpp backs --verify, profile.cpp drives profiling. None of it cares how the engines are launched.
Everything the user touches. The runtime library, andesim/ROI.h, the container image, the per-engine vsim builds.

The order

Cycle mode is the first mode that can work, and it is a real milestone rather than a checkpoint: it needs only one new module, and it proves the hardest mechanical change before anything depends on it.

S0
small · andesim only

Pin the number before anything moves

The cycle count is the product, and any change under the core can move it silently. Record kernel_cycles for a set of fixtures as a golden baseline first. Write down the fidelity contract in the two halves people confuse: the bytes of guest RAM may move to gs_memory, but the response latency reaching the core must not change — and that latency is not produced by the RTL, SimpleMemory adds it (vsim src/platform/simple_memory.hpp:62).

Done when the baseline test fails if a fixture's cycle count moves by one cycle.
S1
large · the hard one

VsimCore becomes a FastSim module → cycle mode runs

Wrap the Verilated core as a moduletype that binds to the router. The pin-to-TLM adapter already exists (vsim src/utils/axi_to_tlm_bridge.hpp), so the work is not the bus — it is who owns sc_start.

Today vsim steps the kernel itself from sc_main: reset() at main.cpp:577, the run loop at simulator.hpp:749, and every DMI transaction at systemc_dmi_bus.hpp:41. FastSim calls sc_start() once and lets the kernel run. sc_start cannot be called from inside the kernel, so all three sites move into an SC_THREAD and become wait().

Two things fall out for free once that inversion is done: an SC_THREAD can wait() on an event, which is what a handoff doorbell needs; and QemuCpu::reset_cb requires an SC_THREAD caller anyway (fastsim models/qemu_components/include/cpu.h).

Done when andesim --mode cycle produces the same cycle count as today, driven by a Lua platform.
S2
medium · fixes the fd bug

One device set → fast mode runs

Assemble the shared platform on -M none, starting from conf/v2_linux_ae350_none.lua, which already carries the whole AE350 board as SystemC modules and boots Linux. Register vsim's SimControl, SMU and UART as moduletypes and bind them to the router; port guest_va_to_host() to gs_memory DMI.

Take -semihosting out of qemu_args. Semihosting is a magic instruction sequence the simulator recognises — a Verilated netlist cannot, on principle. The MMIO mailbox is the only channel both CPUs have, so it is the one the shared platform keeps.

Done when andesim --mode fast runs on the Lua platform, and a file the guest opened is still readable after a mode switch.

Deletes: the second implementation of 18 syscalls patched into QEMU's andes_ae350.c, and the guest-fd bug — not by transporting the fd table, but by there being one process and one table.

S3
medium · needs new libqemu-cxx

State exchange → hybrid mode runs

Memory needs no transport: both CPUs address the same gs_memory. Registers still do, and this does not get simpler — a Verilated netlist has no register setter, so the debug module stays the only architectural write port and the whole DMI resume path survives intact.

Getting registers out of QEMU is the new work. Two blockers, below. Sequencing follows a pattern already in the tree: an MMIO write from the QEMU side, gs::async_event::async_notify(), an SC_THREAD waking on the kernel thread — exactly how StopperV2 and QemuInstance's guest-exit work.

Done when --verify still matches the QEMU oracle, and the hybrid cycle count matches the recorded S0 baseline.
S4
medium · the payoff

CLI over Lua, and the deletion

Translate the 28 options into Lua parameters and CCI presets, then remove the six files above. The exit path has a ready-made pattern: FastSim's multi_arch_toplevel.cpp calls sc_start() once and then scans broker parameters for .failed and .guest_exit_status to build the process exit code.

Done when every AndeSim command behaves as it does today, and driver/ no longer spawns a process.

Blockers found in the source

TCG plugins are compiled out

AndeSim drains state with a TCG plugin, but FastSim's QEMU cannot load one. meson_options.txt:84 defaults plugins to false, and configure:248 takes it from default_feature, which --without-default-features in fastsim CMakeLists.txt:139 sets to no. The plugin does not port as-is.

qemu::Cpu has no register access

It exposes halt, reset, set_soft_stopped, async_safe_run and as_rw for the CPU's address space — and nothing for GPRs or CSRs. Prefer adding an accessor to libqemu-cxx over re-enabling the whole plugin subsystem: as_rw is precedent, added by Andes for exactly this class of need.

The RAM alias bases disagree

vsim puts the uncached alias at 0x8_0000_0000 (memory_map.h); QEMU's AE350 puts UNCACHEABLE_ALIAS at 0x1_0000_0000. Two separate maps hide this today; one router will not. A wrong alias corrupts data silently instead of faulting — reconcile it in S2, before anything runs on the shared map.

PLIC and PLMT freeze while the RTL runs

They are the only AE350 devices with no SystemC implementation anywhere, and the wrapped versions keep their state inside QEMU. Halting the QEMU CPU stops its quantum keeper, so mtime does not advance for the whole measured region. Fine for a bare-metal region that reads no timer; not fine for a Linux one. Port PLMT when a Linux region is actually needed — it is small.

Two engines in one process share symbols

Already hit once in FastSim: STB_GNU_UNIQUE binds vague-linkage statics process-wide even under RTLD_LOCAL | RTLD_DEEPBIND, and tools/ace/rebind_unique_symbols.py rebinds 232 symbols per simulator to work around it. If AndeSim ever loads more than one engine build at once, this is waiting.

Still open

Must the accurate engine always be the RTL?

FastSim already ships a per-instruction cycle model (libacefsim_rv64.so, riscvhf::CycleModel). Where that accuracy is enough, those cases work today and never need S1 at all. Where the product is RTL-derived confidence, S1 stands. This changes the plan's size, not its shape — but it decides how urgent S1 is.

Which vsim engine builds must coexist?

Today each engine is a separate process, so the question never came up. One process makes it real, and the answer sets whether the STB_GNU_UNIQUE workaround becomes part of AndeSim rather than a FastSim curiosity.
