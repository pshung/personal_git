-The orchestrator commands you can run by hand:
-
+./andesim run --mode hybrid --trigger marker --engine vsim:ax45mpv_premium --verify your_prog.elf
+# ...
+# [marker window_cycles] 46  (vsim mcycle=... - qemu mcycle=...)
+# [state-diff] PASS: 109 fields match (counters and passthrough CSRs excluded)
+# [verify] PASS: vsim drain matches the QEMU oracle
+```
+
+Performance note: without `--verify`, the vsim leg drains only `mcycle`/`minstret`
+(the cycle figure) and skips reading back the full architectural register file
+over the Debug Module. A full drain reads every GPR, FPR, and transported CSR
+with one Abstract Command each (only the vector registers ride a Program-Buffer
+sweep through the shared scratch page); those simulated debug cycles dominate
+hybrid wall-clock for a short ROI but never affect the cycle count -- the
+counters are read before the rest of the drain. `--verify` needs every field
+for the diff, so it keeps the full drain; expect a `--verify` run to take
+noticeably longer than the same run without it.
+
+How it works: after the normal run, the same ELF re-runs on pure QEMU (the
+oracle) with the plugin draining at the ROI exit boundary, sampled at the
+exact pc where vsim halted. The pre-ROI path is QEMU in both runs, so the
+ROI inputs are identical -- any architectural divergence inside the ROI
+(RTL bug, state-restore bug, drain bug) shows up as a field mismatch and
+the run exits non-zero, listing each differing field:
+
+```
+[state-diff] x10: ref=0x3d got=0x0
+[state-diff] FAIL: 1 mismatch(es) (115 fields compared)
+```
+
+What is compared: pc, all GPRs, all FPRs (when FP state is live), the V
+CSRs and full vector registers (when V state is live), and the writable
+M-mode CSRs that round-trip through the handoff -- `mscratch` (L23) and
+`mepc`/`mcause`/`mtval`/`mie` (L24), restored at resume and re-read at
+drain. What is not:
+
+- `mcycle`/`minstret` -- the engines count differently by design;
+- `mip` -- restored and re-read, but its pending bits are hardware-driven
+  (the timer bit tracks elapsed time, which differs between QEMU's
+  functional clock and vsim's cycle clock), so a compare would
+  false-positive;
+- `mstatus`, `mtvec` -- passthrough: vsim restores the QEMU1 entry snapshot value; both sides hold the same bits by construction so comparing is trivially true but not useful;
+- `satp`, `medeleg`/`mideleg` -- S-mode CSRs, not implemented on the default M-only engine. The privilege level itself IS compared: both
+  sides drain the real one (L6), so a wrong-privilege resume shows up as
+  a priv mismatch.
+
+The handoff also carries the **v6 write-mask**: the plugin tracks which config
+CSRs (the Andes block, PMA, the M-ext block, `mcache_ctl`/`mmisc_ctl`) your
+program actually WROTE, and the cycle engine restores -- and `--verify`
+compares -- only those. A CSR the program never touched keeps the engine's own
+reset value instead of inheriting QEMU's reset default, so reset-value
+differences between QEMU and any engine cannot skew the run. The tracking is
+translation-time work in the plugin (only CSR-write instructions get a
+callback), so the fast leg's speed is unaffected.
+
+The write-mask also powers an **incompatibility warning** on every hybrid run
+(not just `--verify`): if your program wrote a config CSR the chosen cycle
+engine does not implement, the driver prints
+
+```
+[andesim] warning: the program wrote CSRs engine vsim:<engine> does not
+implement: <names> (on this engine's silicon these writes would trap; the
+hybrid restore skipped them)
+```
+
+to stderr. On that engine's real silicon the `csrw` would trap before the ROI,
+so the cycle figure may not represent this program on this engine -- pick an
+engine that implements those CSRs, or drop the writes. A clean run prints
+nothing.
+
+The handoff also carries the **v5 L2C block**: the L2 cache controller's MMIO
+register window (0x0000..0x0527, base 0xE0500000). This is device MMIO, not a
+CSR -- the QEMU plugin reads the window by physical address, and vsim writes back
+only the writable boot-static config registers (Control 0x0008 = `CEN` enable +
+prefetch + ECC + RAM timing, HPM Control, Way Allocation Masks) via
+Program-Buffer stores before resuming. It is the L2 analog of the L1 `mcache_ctl`
+transport and matters for the cycle figure the same way: an L2-enabled engine
+that resumed with L2 disabled would run the ROI severalfold slower. Restore is
+gated on the cycle engine actually having an L2C (`NDS_L2C_CACHE_SIZE_KB > 0`);
+every engine shipped today is built without one, so the block rides
+forward-looking and no-ops. `--verify` compares the Control Register (masking the
+read-only INITSTATUS bit).
+
+The handoff also carries the v3 Andes block (`mxstatus`, ILM/DLM bases, PMA, ...)
+and the **v4 M-ext block** (`HYBRID_M_EXT_CSR_LIST`): the writable M-mode CSRs
+across the whole AndeStar V5 SPA -- perf counters, NMI, CLIC, trap-save,
+state-enable, debug triggers, ePMP, CCTL, peripheral bases, U-mode Andes control
+(51 CSRs). Every one is **capability-gated by CSR address**: an engine restores,
+drains, and `--verify`-compares only the CSRs its config implements (reported via
+`--describe andes_csrs`), so a CSR the core lacks is a no-op rather than a DM
+hang. On the default `ax45mpv_premium` (M-only) that gates on the perf-monitor +
+trigger CSRs; the rest ride forward-looking for a CLIC / Smrnmi / Smstateen /
+M+U-capable engine. A few supported-but-engine-divergent CSRs are transported and
+restored but excluded from `--verify` (like `msp_bound`): the HW perf counters
+`mhpmcounter3-6`, `mdcause`, the trigger defaults `tdata1`/`tcontrol`, and the
+ILM/DLM base+enable CSRs `milmb`/`mdlmb` (their enable bit reads 1 on the vsim
+RTL but 0 on QEMU, which models no local memory). The
+complete per-CSR disposition for all 232 spec CSRs is in
+`docs/csr_coverage.ipynb`, guarded against drift by
+`tests/andes_csr/check_coverage.py`.
+
+Per-engine CSR validation is a registration requirement: every supported
+engine build carries its own CSR manifest + registration report under
+`tests/engines/` (contract: `tests/engines/README.md`). For a human-readable
+answer to "which CSRs does this engine restore, and under which condition --
+or why not", read the engine's `csr_restore_table.md` in the same directory
+(generated from the manifest by `tests/engines/render_restore_table.py`;
+`test_restore_table.sh` guards it against drift).
+`docs/engine_registration_tutorial.ipynb` walks the whole lifecycle --

+config, and removing one. `docs/csr_transport_bringup_tutorial.ipynb` is the

+

-`./hsim estimate <elf>` runs the full pipeline (M4 BBV profile -> SimPoint
-cluster -> per-phase QEMU+vsim drain) and aggregates a weighted CPI to
-project a cycle count for the whole program:
-
+**cycle model** -- resets and **halts** the hart (like QEMU's `-S`), opens vsim's
+JTAG bitbang port in the background, waits for it to come up, then execs `$ICEMAN`
+-- your JTAG debug server -- in the foreground:
 ```sh

-```
-

-libgloss_vh semihosting EXIT). The plugin counts every retired insn via a
-per-insn TCG callback and writes that count into the drained state file's
-`minstret` field; hsim uses it as `N_total` in:
-
-```
-CPI_i           = delta_mcycle_i / vsim_icount
-weighted_CPI    = sum_i ( w_i * CPI_i )
-estimated_cycles = N_total * weighted_CPI
-```
-
-Pass `--icount N` (positive) to instead cap the profile pass at N insns
-and use N as the multiplier (useful for very long-running workloads
-where you only want to characterize the first N insns).

+## 5. One binary on every engine (the vplat runtime)
+
+A binary linked with a semihosting libgloss (e.g. `-lgloss_vh`) can print
+only where a QEMU intercepts the semihosting `ebreak` triple; vsim has no
+semihosting, so a syscall inside the ROI traps there -- the old Phase-2
+"no syscalls inside the ROI" rule. The **vplat runtime** removes the
+per-engine build split: it is a newlib stub layer
+(`runtime/vplat_syscalls.c`) that talks only to devices both
+engines model at the same addresses, so ONE ELF runs on `fast`, on `cycle`,
+and across a `hybrid` handoff, and a syscall inside the ROI works (it just
+adds its real cycles to the figure). Every in-tree C fixture links this
+runtime; nothing in the repo uses `-lgloss_vh` anymore.
+
+| Channel | Device | QEMU andes_ae350 | vsim |
+|---------|--------|------------------|------|
+| stdio (fd 0-2)   | UART2 16550, `THR` @ `0xf0300020`, `LSR` @ `0xf0300034` | `serial_mm_init` (serial0) | `src/platform/uart.hpp` |
+| exit code        | SimControl @ `0xe0080000` (u32 < 256 = exit code)       | `hw/misc/andes_sim_control.c` | `src/platform/sim_control.hpp` |
+| file io (fd > 2) | HTIF magicmem command @ `0xe0080010`                    | same device | same model |

-**Picking `--slice`** (insns per BBV row). One BBV row is the smallest
-unit SimPoint can cluster. Too few rows -> k-means cannot find structure.
-Too many rows -> long profile pass and long clustering. Aim for ~20.

-| Program size (N_total) | Pick `--slice`  |
-|------------------------|-----------------|
-| < 10K (toy)            | 500             |
-| 10K..100K              | 1000..5000      |
-| 100K..1M               | 5000..50000     |
-| > 1M                   | 50000+          |

-**Picking `--max-k`** (number of phases). Each phase costs **one extra
-QEMU+vsim drain pair** (~5..10s). SimPoint will sometimes pick fewer
-phases than `--max-k` if the workload is uniform, so `max-k` is an upper
-bound, not a fixed count.
+`-B` points gcc at the built artifacts (use the absolute path to
+`<repo>/build/runtime` when compiling outside the repo);
+`-specs=andesim.specs` swaps the startfile to the runtime's `crt0.o`,
+adds `-T andesim.ld` (load base `0x00100000`), and rewrites the library
+list to `--start-group -landesim_runtime -lc -lgcc --end-group`, so no
+libgloss or semihosting can leak into the link.
 
-| Workload structure              | Pick `--max-k` |
-|---------------------------------|----------------|
-| Single loop kernel              | 2 (init + body) |
-| Init + kernel + cleanup         | 3              |
-| Multi-kernel (e.g. 2 GEMMs)     | 4..6           |
-| Large benchmark mix             | 8..16          |

-**Sanity checks after a run.** Read the per-phase rows and apply:
-
-1. `BBV rows >= 2 * max_k`. If fewer, drop `--slice` so more rows fit.
-2. Weights add to ~1.0 and are not all small. If all `--max-k` phases
-   have similar weights, the workload is uniform and you can drop `max_k`.
-3. CPIs differ across phases. If every phase reports the same CPI, you
-   are paying for vsim time without gaining accuracy. Drop `max_k`.
