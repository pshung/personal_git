Where this runs

One core, one wide vector unit, no L2

The target is an Andes AX46MPV RISC-V core. It is not silicon yet: it is RTL, simulated cycle by cycle. That is the single fact that shapes everything below. Nothing here is guessed from a model of the pipeline, and nothing here is a wall-clock time either - the simulator runs at a few kHz, so every number on this page is a cycle count.

Two properties of this core drive every decision. The vector unit is wide - 1024 bits, so 128 int8 lanes in one register - and the memory system behind it is thin: 32 KB of L1 data cache, no L2 at all, and a 2 MB L3. A kernel that keeps the lanes busy wins twice, because it also spends fewer trips through that memory system.

253 Q1_0 tensors is exactly 36 layers x 7 + 1. The +1 is the LM head, and it is a single tensor holding 9.7% of all the weights in the model. Keep it in mind; it decides the ending.

Producing one token means running all 253 of those matmuls. Norms, RoPE, softmax and sampling are also there, but next to 4.02 G weight-multiplies they are rounding error. Speeding up this model means speeding up one function.

That function runs in two different shapes, and they behave differently enough that every number on this page is reported twice:

Decodegemv, one column

Generating text, one token at a time. The weight matrix is multiplied by a single activation vector. Every weight is read from memory, used once, and thrown away - so this shape is naturally starved for memory bandwidth.

Prefillgemm, four columns

Reading the prompt, many tokens at once. The same weight matrix is multiplied by four activation vectors at a time, so each weight that arrives is used four times. More arithmetic per byte loaded, and a different bottleneck.

ggml picks between them on the spot: more than three columns of activations goes to the gemm, the leftovers go to the gemv. Both read the exact same weight bytes, so any change to the layout has to serve both.

How we measure

Count one node, not one token

An RTL simulation is far too slow to generate a token end to end and time it. So we do not. andesim hybrid mode runs the whole program on a fast functional model, and when the program hits a marker it hands the machine state over to the RTL engine, which counts real cycles until the closing marker.

The markers sit around one MUL_MAT node, picked at compile time. Nothing else in the model can pollute the number, and the same node can be re-measured for every build. Every stage below is a separately built binary run with an identical command line.

Inside the measured windowpaid on every token
  • Quantizing the activations from float down to 8-bit. The baseline pays this too, so the comparison is like for like.
  • Expanding the 64 fp16 row scales to fp32, once per weight block.
  • Restaging or de-interleaving the activation quants, from stage 04 on.
  • The gemv or gemm itself.
Outside itpaid once, at model load
  • The weight repack. It runs inside the buffer's set_tensor while the model file is being read, before any graph executes. The ROI markers are not armed yet.

Not measured on the target, but bounded from the generated code. The repack loop is scalar and runs once per weight bit: extract the bit, compute the destination index, read-modify-write one byte. Compiled for rv64 at -O2 that inner loop is 16 instructions per bit in the stage 02 order and 21 in the stage 04 order, with no unrolling.

That is a real cost and it lands entirely on time-to-first-token - on the order of a hundred tokens of payback. The same loop takes 4.5 s on an x86 host, where out-of-order execution hides the read-modify-write chain; this core cannot.

It is also fixable, and nobody has tried: cache the repacked buffer on disk so it becomes a build step, or vectorize the bit transpose using the same mask operations the kernel itself uses. Splitting it across threads is not an option on this engine - it has one hart.

  • Correctness 13 shape cases in tests/test-repack-q1_0, run against both layout orders. Stages 03, 04 and 05 are bit-identical to stage 02, not merely within tolerance.
  • What is not here Tokens per second, and any statement about a clock frequency. Neither is knowable from an RTL run, so neither is claimed.

The problem

A multiply that is not a multiply

A Q1_0 block holds 128 weights in 16 bytes, one bit each, plus one fp16 scale. Bit set means +1, bit clear means -1. The activations are Q8_0: 32 int8 quants and one fp16 scale.

So the inner operation is not a multiply-accumulate. It is add or subtract the activation. There is no arithmetic left to optimize. The entire cost of this kernel is decided by two questions: how many lanes are doing useful work, and how many instructions it takes to feed them.

The stock kernel answers both badly, and it is not a tuning problem. The weight layout it inherits from the file format forces the answer.

Upstream baseline - ggml_vec_dot_q1_0_q8_0

One row at a time, and a reduction every 32 columns

Because a block is one row of 128 columns, the natural kernel loads part of one row, multiplies it against the activations, and adds the results together. That last step is the problem: adding up numbers that live in different lanes of the same vector register is a horizontal reduction, and it is serial.

A vwredsum is a serial tree. Doing 80 of them per output row is the single biggest thing wrong with this kernel, and no amount of tuning inside the loop removes it. The layout has to change.

02

Repack, standard RVV - block_q1_0x64

Put 64 rows in the lanes and the reductions disappear

decode 2,144,213 2.09x prefill 1,696,704 5.23x 0 horizontal reductions

Symptom

32 of 128 lanes busy, and 163,840 serial reductions in this one node.

Change

Transpose the sign bits at load time so lane j holds row j, not column j.

Effect

2.09xThe reduction over K becomes a vertical add inside each lane. Zero horizontal reductions remain.

Turn the tile 90 degrees. If each lane owns one output row, then summing over the K dimension is just adding into that lane over and over - a loop-carried vertical add, which costs nothing extra.

For that to work the bits have to be rearranged so that one mask load gives one column across all 64 rows. That is the repacked block: the same 1152 bytes as 64 original blocks, permuted. No weight data is added or removed.

LMUL follows VLEN so the 64 fp32 accumulators exactly fill the machine: i16 m1 / f32 m2 at VLEN=1024, i16 m2 / f32 m4 at VLEN=512.

Constraint solved

No zvfh needed

The 64 fp16 row scales are expanded to fp32 with plain integer bit math, and the int16 group sums are widened with vsext + vfcvt rather than vfwcvt.f.x.v, which some RTLs reject. The kernel runs on a zve32f machine.

The gate this creates

Rows must be a multiple of 64

64 rows per lane group means a tensor whose row count is not divisible by 64 cannot be repacked, and silently falls back to the stage 01 kernel. In this model exactly one tensor fails: the LM head, [2560 x 151669], because 151669 mod 64 = 53.

New bottleneck The arithmetic is now nearly free, which exposes what was hidden behind it. The gemv streams 1152 fresh bytes per block and never reuses any of them, so the kernel spends its time waiting for memory.

03

Software prefetch - zicbop

Ask for the next block before you need it

decode 1,389,236 1.54x over 02 prefill 1,651,949 1.03x results unchanged

Symptom

Decode stalls on weight loads. Each block is 18 cache lines, read once, never reused.

Change

At the top of block l, issue 18 prefetch.r hints for block l+1.

Effect

1.54xon decode. Prefill barely moves, because its four-row tile already hid the stall.

Why the hardware cannot do it

The core's hardware prefetcher is shallow by design: 4 D-cache prefetch entries and L3 line prefetch disabled. With no L2 behind the 32 KB L1, it cannot run far enough ahead to cover an L3 or DRAM round trip on a stream this wide.

; top of block l, 18 lines of block l+1 for o in 0, 64, ..., 1088: prefetch.r (&bx[l+1] + o)

Pure hint. The numbers coming out of the kernel do not change at all.

04

Andes V5 XAndesVDot - nds.vd4dots.vv

One instruction, 256 multiply-accumulates

decode 457,092 3.04x over 03 prefill 931,754 1.77x bit-identical to 03

Symptom

One vector op per column. 21 MACs retired per instruction, and four load operations per 32 bytes of mask.

Change

Permute the bits once more so four columns fit one register group, and use the core's own 4-way dot instruction.

Effect

3.04x64 MACs per vector op, and a quarter as many mask loads for the same bytes.

nds.vd4dots.vv is a stock Andes vendor instruction on this core, not a custom extension we had to design. At e32 it computes, for every 32-bit lane:

vd[j] += vs1[4j+0]*vs2[4j+0] + vs1[4j+1]*vs2[4j+1] + vs1[4j+2]*vs2[4j+2] + vs1[4j+3]*vs2[4j+3] ; int8 x int8 accumulated into the i32 lane ; vd, vs1, vs2 all at the same LMUL

Here is the piece of luck that made this stage work. At VLEN=1024, e32/m2 is exactly 64 i32 lanes = 64 rows, and that same register group seen as bytes is 256 bytes = 64 rows x 4 columns. The instruction's operand shape and our repacked tile are the same object. All that was left was to make the bits arrive in that order.

The same instruction, tiled two ways

Decode multiplies by one activation vector, prefill by four at once. The dot is used the same way in both, but which operand gets reused flips - and that decides how the 32 vector registers are budgeted.

One authority

The layout cannot drift

Both bit orders live in one function, q1_0x64_sign_bit(). The repack writer and every reader call it. A numeric test can never catch a layout mistake here - writer and reader would share the bug, so it cancels. Only a codegen gate can.

gemv activation side

Restage, do not gather

The dot wants 4 activation quants as one 32-bit element, but block_q8_0 puts qs at offset 2, so every other group sits at 2 mod 4 and the core faults on a misaligned 32-bit vector element load. Copy the quants once per call through byte load/store (EEW=8 has no alignment rule). Under 1%.

gemm activation side

De-interleave with vnsrl

The 4-row activation block stores qs[c*4 + m], but row m needs its four columns contiguous - a stride-4 gather. Instead peel the byte lanes apart once per row tile with vnsrl (u32 to 2x u16 to 4x u8): 6 shifts and 4 stores per 32 columns, reused by every column tile.

New bottleneck With the dot in place, the loop body is small enough that its overhead is visible. Reading the generated assembly showed 40% of the gemv's inner loop was not arithmetic at all.

05

Codegen - the vtype churn

Forty percent of the loop was changing element width

decode 362,799 1.26x over 04 prefill 818,314 1.14x the math did not change at all

Symptom

Four vsetvli per dot in the gemv. They do no arithmetic; they only re-describe the registers.

Change

Put every 32-bit operation, broadcasts included, inside one inline asm block so the compiler only has byte-width work left to schedule.

Effect

1.26xdecode, 1.14x prefill, from 4.00 down to 0.94 vsetvli per dot. Not one line of math was touched.

The kernel keeps switching between two views of the same registers: the byte view for the mask load and sign expand, and the 32-bit view for the broadcast and the dot. Every switch needs a vsetvli. GCC makes it worse: it cannot see inside an inline asm block, so it assumes each one left vtype unknown and re-issues its own on top.

Did not work

Grouping the two widths in the source

Writing all four mask loads first and all four dots after only got the gemv from 4.00 to 2.00. The scheduler interleaves them again. The fix has to be inside a single asm block, where the scheduler cannot reach.

Did not work

Four scratch registers instead of two

The idea was to double the distance between each broadcast and the dot that consumes it. No spills, 4.06 instructions per dot instead of 4.13 - and 4.5% slower (855,476 versus 818,314). Producer-consumer distance is not what limits the gemm. Reverted.

After this stage the two paths are bound by different things. Cycles per issued instruction: the gemv went 2.23 to 2.24 - unchanged, so it is purely instruction-issue bound and every instruction removed became a cycle saved, one for one. The gemm went 2.53 to 4.84. It is no longer issue bound: roughly 11 cycles per dot are stall, and cutting more instructions will not help prefill.

Also shipped

Three traps that delete the win, silently

Each of these produced correct results while removing the optimization, so no numeric test could ever see it. Each one now has a comment in the source and a script that fails the build.

Trap 01 - 18x

The stride-0 broadcast

Handed "load a word, then splat it", GCC contracts the pair into vlse32.v vd,(rs1),zero. A stride-0 strided load is element-serial on this core. Since stage 05 the broadcast is written by hand as vmv.v.x inside the asm block, taking the quads as plain GPRs, so the contraction is impossible.

Trap 02 - fault

Misaligned vector element load

The core faults on a misaligned 32-bit vector element load. block_q8_0 puts qs at offset 2 and is 34 bytes, so every other group is 2 mod 4. Restaging through byte load/store fixes it; the 4-row activation block is 4-byte aligned and needs no restaging.

Trap 03 - silent DCE

always_inline is load-bearing

A prefetch has no observable effect, so whenever the compiler leaves the helper out of line, ipa-pure-const marks it pure and dead-code elimination deletes every call. No warning, results still correct. GCC 14.2 does exactly this at -Os, which had silently removed the entire stage 03 win from the MinSizeRel build.

Two of the thirteen exist only because they are the only shapes where the gemm's row-tile loop advances more than once, so they are the only ones that check the activation and output strides. Stages 03, 04 and 05 are bit-identical to stage 02 - every error figure is unchanged, not merely within tolerance.

Correction on the record

The "instruction-issue floor" was not one

At stage 04 the fastest configuration measured was 328,865 cycles, with weights in local memory, and it was written down as an instruction-issue floor. It was not a floor - it was an instruction count. Stage 05 beat it at 362,799 with no local memory at all, and stage 05 plus local memory was never measured.

What it adds up to

The node got 9.8x faster. The token got 5.6x faster.

A per-node speedup is not a per-token speedup, and the gap is the most useful thing on this page. Scaling the measured layer 7 across all 36 layers, and adding the one tensor that was never repacked, gives the Q1_0 cost of generating a single token.

How the LM head figure is derivedestimate, not measured

The stage 01 kernel costs a very steady 1.69 to 1.72 cycles per weight across every K=2560 node in the measured sweep. The LM head is [2560 x 151669] = 388 M weights and runs that same kernel, which puts it near 0.66 G cycles. It is the only number on this page that is scaled rather than measured, and it is marked as such.

Why it was skipped151669 mod 64 = 53

The repack groups rows 64 at a time, so a tensor whose row count is not a multiple of 64 is rejected and falls back to stage 01. This model ties its output projection to the token embedding, and the vocabulary is not a round number.

At stage 01 it was 9% of the token. At stage 04 it is 52%. Optimizing everything else made the one thing we did not optimize into the dominant cost - which is exactly what should happen, and exactly where to go next.

Handling a row remainder is not exotic: process the last partial group of rows with the stage 01 kernel and repack the rest. That single change is worth more than any further tuning of the kernels on this page.

Open

What is left

In rough order of how much they are worth.

  • The LM head Half of an optimized decode pass, running the slowest kernel, because of a row count that is 53 short of a multiple of 64. Needs a remainder path in the repack gate, not a new kernel.
  • Load-time repack 76 G scalar instructions before the first token, single-threaded because the core is single-hart. A disk cache or a vectorized bit transpose removes it. Neither has been tried.
  • Prefill's stall About 11 cycles per dot are stall, cause not established. Two build targets already exist that would settle it: prefetch off, and weights in local memory, both on the prefill node. If neither moves the number, the limit is the dot's own throughput at e32/m2 and prefill is done until the ISA changes.
  • Local memory Worth 1.39x at stage 04 and never re-measured since. The caveat cuts the other way for big models: attn_v's 360 KB working set fits the 2 MB L3, but a 27B ffn_down is 12 MB per tensor, where L3 is useless and local memory should be worth more.
  • A 1-bit weight operand The remaining pot on decode is compute, not memory. An instruction taking the sign mask directly would drop the vmerge and cut weight register traffic by 8x. It attacks a different bottleneck than local memory, so the two stack.
  • VLEN=512 The second engine, ax45mpv_premium, needs the e32/m4 shape of the same kernel. Blocked on a hybrid-mode halt bug on that engine, not on the kernel.
