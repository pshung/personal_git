                    27.3.6            NDSROM.datImageFile
                    The ROM image ﬁle NDSROM.dat serves as the test pattern for each test case. Its format is deﬁned
                    by the SystemVerilog $readmemh() system task. The default make target does not regenerate the
                    ROMﬁle. Instead, the make rom target is used to regenerate the NDSROM.dat ﬁle.
                    For the make rom target to work, the toolchain programs (riscv64-elf-ar and riscv64-elf-
                    gcc) should exist under the directory speciﬁed by $NDS_TOOLCHAIN, e.g.,
                    setenv NDS_TOOLCHAIN <directory of toolchain>/riscv64-elf-mculib/bin
                    Note that the toolchain programs (riscv64-elf-ar and riscv64-elf-gcc) are not included in
                    the AX66 release package. Find them in the AndeSight software development tools.
                    Thetoolchains convert assembly or C programs to a.out ﬁles. To make the executable ﬁles loadable,
                    a.out must be further converted into ﬂat binary data and then into the ASCII format readable by
                    the $readmemh() SystemVerilog system task. riscv-elf-aout2mem demonstrates this process
                    for simple a.out formats containing simple .text and .data sections. riscv-elf-aout2mem comes
                    with the AX66 distribution and can be found as $NDS_HOME/tools/bin/riscv-elf-aout2mem.
                    It is a straightforward sample Perl script. If advanced linker sections are used, the riscv-elf-
                    aout2memprogrammayneedtobemodiﬁedtosupportextrasections.
                    EachelementofthearrayinNDSROM.datisinthebig-endianformatregardlessofthesystemendian.
                    That is, bytes 0 (0x00), 1 (0x11), 2 (0x22), and 3 (0x33) of the binary image will be represented as
                    0x00112233 at index 0 of the array.

                    27.3.9            Simulation Control
                    Thesepatternsruninaself-checkmanner. Ifanunexpectederrorisdetected,theprogramwillwritea
                    speciﬁc value to ahb_sim_control to terminate the simulation early. If the test completes successfully,
                    the program writes another speciﬁc value to ahb_sim_control to gracefully terminate the simulation.
                    Onthehardware side, ahb_sim_control achieves this by snooping AHB trafﬁcs on the internal subor-
                    dinate (subordinate 0) of the AHB Decoder. This internal subordinate is allocated a 1 MiB space (see
                    Table 124) but uses less than two hundred bytes. By default, the BASE parameter of ahb_sim_control
                    is set to 0x80000, meaning it only checks offset addresses beyond 512 KiB in this 1 MiB space. This
                    guarantees the existence of ahb_sim_control will not interfere the normal operation of this internal
                    subordinate.
                    If the base memory address of this 1 MiB space is changed, the monitored space of ahb_sim_control
                    will also be changed, since the snooping relies directly on the internal signals after address decoding
                    inside the AHB Decoder. This 1 MiB space must reside in the device region, ensuring the memory
                    space of ahb_sim_control is also within the device region.
                    When ahb_sim_control detects an AHB write transaction to the BASE offset with certain recognized
                    values of write data, it prints related pass/fail information and calls Verilog system task $finish to
                    terminate the simulation. Details of ahb_sim_control are listed in Table 187.
