-## Repository Overview
-
-Andes hybrid RISC-V simulator: QEMU 9.x (functional, MHz-level) + vsim (SystemC + Verilator, cycle-accurate) share architectural state across a magic-CSR boundary. The system runs a two-phase handoff: **QEMU1** (drain on CSR/PC trigger) -> **vsim** (resume + execute + drain). The cycle figure is the vsim `mcycle` delta; there is no QEMU2 leg (the handback was removed).
-
-One Git submodule:
-- `include/` - the shared ABI (`andesim_abi` repo): the `hybrid_state_v1` wire
-  contract under `include/hybrid/`, pinned by andesim AND by the external vsim, so
-  there is one source of truth.

-- QEMU: point `QEMU_BIN_DIR` (config.env) at your `qemu-system-*` build dir.

-## Architecture
-
-### Two-Phase Handoff
-
-```
-QEMU1 --(state file + shared mmap)--> vsim (resume + run ROI + drain)
-```
-
-1. **QEMU plugin** (`qemu_plugin/hybrid_handoff.c`) - TCG plugin. On the marker trigger (`slti x0, x0, 0x5A0`) or PC-trigger, drains QEMU's architectural state into a binary `hybrid_state_v1` struct written to `--outfile`.
-2. **vsim handoff controller** (`src/hybrid/handoff_controller.hpp`) - Detects the trigger inside vsim, pauses the hart via DMI, then calls `ResumeDriver` to restore state.
-3. **ResumeDriver** (`src/hybrid/resume_driver.hpp`) - Writes GPRs/FPRs into the vsim hart via RISC-V Debug Module Abstract Commands, one write per register. Every CSR write -- the base M-mode scalars, the Andes V5 block, and the M-ext block -- also goes through Abstract Commands only, one write per CSR; there is no batched Program-Buffer sweep anywhere in the register/CSR transport, in either direction (a WARL/read-only CSR faulting mid-batch can't be tolerated the way the abstract path's per-CSR cmderr-clear can). `StateDrain` mirrors this: one abstract read per GPR/FPR/CSR. The Program Buffer carries only state the abstract command space cannot reach: the V-data sweep, `vtype`+`vl` (Tier B, see V-State Transport below), and the L2C MMIO window. **Liveness gate**: restores whose drained value equals the engine's own reset value are skipped (a no-op write; each DM op costs ~200-900 simulated cycles). The reset baseline is drained once per (engine build, ELF) on the first hybrid run and cached under `$XDG_CACHE_HOME/andesim/`; `--no-reset-baseline` disables. Never gated: mstatus, GPRs, dpc, dcsr, mcycle, minstret, the S/U PMP mirror. Verify-transparent by construction (skip only when the value is already there).
-4. **StateDrain** (`src/hybrid/state_drain.hpp`) - On vsim exit trigger, reads back the full architectural state via DMI Abstract Commands into `hybrid_state_v1`. This is the end of the run: the cycle figure is the vsim `mcycle` minus QEMU1's drained `mcycle`. The old QEMU2 resume leg was removed entirely.
-
-**CSR restore split**: `ResumeDriver` writes the CSRs the vsim phase can touch: `mstatus`, `mtvec`, `mscratch` (L23), `mepc`/`mcause`/`mtval`/`mie`/`mip` (L24), `mcycle`, `minstret`, `fcsr` (frm + sticky fflags, gated on `HYBRID_FLAG_FP`; L20), and the Andes machine-setup CSRs `mcache_ctl` (0x7CA) + `mmisc_ctl` (0x7D0) (L21). The cache pair matters for the cycle figure, not correctness: crt0 enables the L1 I/D caches via `mcache_ctl`, but that write runs on the cache-less functional engine, so without transporting it vsim resumes at the ROI with caches at their reset default (disabled) and the whole window runs uncached -- inflating the cycle count severalfold. All are tolerant writes: an engine without a given custom CSR mirrors the write as a no-op. In the trap-free ROI these writable M-mode CSRs are ordinary read/write state, so they round-trip fully: restored at resume, re-read at drain (`StateDrain::drain_with_passthrough`), and compared by `--verify` (`state_diff`). Two verify-side exceptions: `mip` is restored + re-read but NOT compared -- its pending bits are hardware/platform-driven (the timer bit tracks elapsed time, which advances differently in QEMU's functional clock vs vsim's cycle clock), so comparing it would false-positive; and `mtvec` is restored but not re-drained. The S/U trap CSRs `medeleg`/`mideleg`/`satp` are drained by the plugin since v1 and, since the ax66 registration (option A), restored + re-read + `--verify`-compared on S-mode-capable engines (caps gate SMODE; the describe list names them); on an M-only engine (`ax45mpv_premium`, `NDS_NUM_PRIVILEGE_LEVELS=1`) they stay drain-record-only. Other S-mode CSRs (`sstatus`, `sepc`, ...) remain deferred to the S/U-envelope work. The vsim phase is assumed trap-free, interrupt-free, and PMP-static; if a future workload needs traps or dynamic PMP inside the ROI, `ResumeDriver` must be extended.
-
-**Privilege (L6)**: the handoff carries the real privilege level. The plugin drains the gdbstub `priv` register, `ResumeDriver` read-modify-writes `dcsr.prv` before `dret` (and verifies the write took -- an M-mode-only RTL like the default `ax45mpv_premium`, `NDS_NUM_PRIVILEGE_LEVELS=1`, WARL-pins the field, and the resume aborts with a pick-an-S/U-capable-engine error), and `StateDrain` reads `dcsr.prv` back at the exit halt. For S/U handoffs the producer's PMP block (64 `pmpaddr` + the 8 even `pmpcfg`) is also mirrored into the hart, because with PMP implemented and no matching entry every S/U access faults; M-mode handoffs keep PMP pass-through-only (L2). The `rt_priv_smode`/`rt_priv_umode` fixtures run on the S/U-capable `ax66_makatau` engine paired with QEMU `-cpu andes-ax66` (see `scripts/run_e2e.sh`); the ROI itself must still be trap-free, single-privilege, and paging-off (S-mode CSRs are not transported).

-### Trigger Modes
-
-The repo ships 2 switching modes (triggers); each measures one region you
-choose. The C++ `andesim` driver exposes them via `--trigger marker|pc`.
-
-- **marker mode** (default): Pattern-matches `slti x0, x0, 0x5A0` (entry) / `slti x0, x0, 0x5A1` (exit) at retire time. The markers are RISC-V HINTs (rd=x0 discards the result), i.e. architectural NOPs -- a marker binary also runs standalone on every engine and on silicon. Users get them from `<andesim/ROI.h>` (`andesim_ROI_begin()/end()`).
-- **PC mode**: explicit boundary PCs passed as `--pc-start S --pc-end E` (symbol name or `0x` address) resolved at startup; marker insns are bypassed. Both args are required.
-
-`./andesim run --mode hybrid --trigger marker|pc` is the unified orchestrator; `tests/e2e.sh` drives marker/pc internally. The run yields a cycle figure: window cycles = the vsim `mcycle` delta (`hybrid_state_v1::mcycle`).
-
-### Shared ABI (`include/hybrid/state_abi.h`)
-
-`hybrid_state_v1` is the binary wire format exchanged between the QEMU plugin and vsim. It holds: 32 GPRs, 32 FPRs, fcsr, M-mode CSRs (mstatus, mepc, etc.), PMP (64 pmpaddr + 16 pmpcfg), the V extension block (vstart, vtype, vl, vlenb, 32 vreg[], vxsat, vxrm, vcsr), (v3) the Andes V5 CSR block `struct hybrid_andes_csr andes`, (v4) the writable M-mode CSR block `struct hybrid_m_ext_csr m_ext`, and (v5) the L2C MMIO register window `struct hybrid_l2c l2c`. `HYBRID_VLEN_BYTES_MAX=128` supports VLEN up to 1024 bits; the live width is the runtime `vlenb`, and a producer whose vlenb exceeds the ceiling refuses to drain instead of truncating (L11). Multi-byte fields are little-endian (native on RV64 + x86-64 host); the format is not endian-portable.
-
-**v3 Andes block**: `struct hybrid_andes_csr` carries the Andes-specific CSRs a bare-metal Andes core sets up before the ROI -- 13 scalar CSRs (mxstatus, mpft_ctl, mclk_ctl, milmb, mdlmb, mecc_code, mhsp_ctl, msp_bound, msp_base, mcountermask_m, uitb, jvt, ucode) + PMA (pmacfg[2] @ 0xBC0/0xBC2, pmaaddr[16] @ 0xBD0..0xBDF). The 13 scalars are defined ONCE by the X-macro `HYBRID_ANDES_CSR_LIST(X)` in `state_abi.h`, which every consumer iterates (plugin drain, `ResumeDriver` restore, `StateDrain` re-read, driver `state_diff` verify) -- so adding a CSR is one line, no consumer drifts. Live only when `HYBRID_FLAG_ANDES` is set (the plugin sets it when QEMU's gdbstub advertised at least one Andes CSR). All restores are tolerant (a core lacking the CSR no-ops the write); the block round-trips through the trap-free ROI and is `--verify`-compared, except `msp_bound`/`msp_base` (HW stack-protection bounds) and `milmb`/`mdlmb` (ILM/DLM base+enable) which are engine-reset-divergent -- QEMU resets `msp_bound`/`msp_base` to all-ones (a vsim core without HW stack protection drains 0), and drains the `milmb`/`mdlmb` enable bit clear while the vsim RTL drains it set -- so they are verify-excluded like `mip`.
-
-**v5 L2C block**: `struct hybrid_l2c` carries the **L2 cache controller's MMIO register window** (`reg[]` = offsets 0x0000..0x0527, DS220 11.8.5 Table 112). Unlike every other block this is DEVICE MMIO, not a CSR: the plugin drains the whole window with `qemu_plugin_read_memory_hwaddr` (physical address `l2c_base`, default 0xE0500000), and `ResumeDriver::restore_l2c` writes back ONLY the writable boot-static config registers -- Control (0x0008: `CEN` enable + prefetch + ECC + RAM timing), HPM Control (0x0010), Way Allocation Masks (0x0300..0x0328) -- via Program-Buffer word stores (`sw`, per DS220 11.8.3's <8-byte access rule). The read-only Configuration Register, the side-effecting CCTL command registers (writing one re-issues an L2 cache op), and the W1C error registers are captured but never restored. `StateDrain::drain_l2c` re-reads the config registers (`lwu`) for `--verify` (`state_diff` compares `l2c.ctrl` with the RO INITSTATUS[14] bit masked). This is the MMIO analog of the `mcache_ctl` (L1-enable) transport, and matters for the cycle figure the same way: an L2-enabled engine that resumed with L2 disabled would run the ROI severalfold slower. **Restore is HARD-gated on the engine having an L2C** (`Simulator::l2c_present()` from `_NDS_L2C_CACHE_SIZE_KB > 0`): a store to an absent L2C region faults the Program Buffer, unlike a tolerant CSR write. Every current engine is built `NDS_L2C_CACHE_SIZE_KB=0`, so the block is transported forward-looking and the restore/drain no-op today. QEMU seeds the L2C Control Register's reset value (`CEN=1`, DS220 11.8.7) at machine init (`andes_ae350.c`), so a guest that relies on the default is not drained as `CEN=0`.
-
-**v6 write-mask**: `write_mask[2]` (one bit per mask-governed config CSR, slot map + decode helpers in `include/hybrid/write_mask.h`, live under `HYBRID_FLAG_WRITE_MASK`) records **which CSRs the guest actually WROTE** during the QEMU phase. The plugin decodes CSR-write instructions at translation time (`csrrw`/`csrrwi` always write; `csrrs/c` only when rs1!=x0; `csrrsi/ci` only when uimm!=0) and registers an exec callback only on instructions that write a mask-governed CSR -- steady-state code carries zero instrumentation, so the fast leg is unaffected. Consumers (`ResumeDriver` restore, `state_diff` verify) skip any governed CSR whose bit is clear: an untouched CSR's drained value is only QEMU's reset default, which can legitimately differ from the engine's RTL reset value (`msp_bound` all-ones vs 0, `milmb.IEN` 0 vs 1), so skipping keeps the engine at ITS OWN reset value -- what real silicon of that engine would hold -- and makes producer/engine reset divergence harmless by construction for every current and future engine, with no per-engine data in QEMU. Governed set: the v3 Andes scalars + PMA, the v4 M-ext block, `mcache_ctl`/`mmisc_ctl`. Never governed: GPRs/FPRs/V, mstatus, dpc/dcsr, counters, fcsr, the trap-writable CSRs (mepc/mcause/mtval/mip/mie -- hardware writes them without a CSR insn), mtvec/mscratch, and PMP (the S/U mirror is a correctness requirement). `ucode` is transport-always (DSP ops set its sticky OV flag without a CSR insn). Flag clear (pre-v6 file) -> consumers fall back to restore/compare-everything.
-
-**Memory-content sidecars (NOT in `hybrid_state_v1`)**: ILM/DLM and HVM content travels OUTSIDE the state struct, as raw binary sidecar files next to each state file. The plugin (args `ilm_size`/`dlm_size`/`hvm_size` in bytes; bases default `0xA0000000`/`0xA0200000`/`0x90000000`) drains `<state>.ilm/.dlm/.hvm` through the slave-port/subordinate apertures; the vsim leg backdoor-loads them (`--ilm/--dlm/--hvm` -- zero-sim-cycle Verilator hierarchical-reference pokes into the RTL SRAMs, NOT the DM Program Buffer); the exit drain dumps the read-duals next to the handoff-out state. Armed by the engine's `--describe` sizes (`ilm_size`/`dlm_size`/`hvm_size`, bytes; 0 = no memory or wrapper lacks the set_*/get_* backdoor pair -- capability-gated so a config-has-it/wrapper-can't engine arms nothing). These QEMU memories are per-CPU overlays (LM) or standalone RAM (HVM), NOT backed by the shared mmap, so the sidecars are the only road their content travels; QEMU's raw geometry must be synced (`-readconfig` on the driver path, `-global` in tests/e2e.sh -- HVM's property is `hvm_size_pow_2`, log2) because QEMU's compiled-in defaults (2 MB ILM at 0x0, 1-BYTE HVM) are wrong for every engine.
-
-Flags (`HYBRID_FLAG_RV64`, `HYBRID_FLAG_FP`, `HYBRID_FLAG_V`, `HYBRID_FLAG_ANDES`, `HYBRID_FLAG_M_EXT`, `HYBRID_FLAG_L2C`, `HYBRID_FLAG_WRITE_MASK`) gate which state blocks are live. The ABI struct is validated by `tests/hybrid/state_abi.test.cpp` (in the external vsim repo).

-### V-State Transport
-
-V data registers (v0..v31) move through a scratch region in the shared mmap.
-L26: that region is the mmap's TOP page, `v_scratch_gpa(ram_base, ram_size) =
-ram_base + ram_size - HYBRID_V_SCRATCH_BYTES`, NOT a fixed address. The driver
-maps one page more than `--mem-size` (`shm.cpp physical_mmap_bytes`), so the
-scratch sits at `ram_base + --mem-size`, just above the program's RAM, where no
-program layout can collide with it (`cmd_run` also rejects an ELF whose static
-image would reach into it). `ResumeDriver`/`StateDrain` take the GPA as a
-required-when-V argument (the simulator passes `v_scratch_gpa()`); a V handoff
-with it unset throws. vsim drives the transfer via the Debug Module **Program
-Buffer** while the hart is halted, so benchmark binaries issue no transport code:
-- `stage_v_to_scratch` copies `hybrid_state_v1::vreg[]` into the scratch region
-  before resume; `ResumeDriver` then sweeps `vle8.v v0..v31` from scratch into the
-  regfile (`pb_v_data_sweep`, load=true).
-- At drain, `StateDrain` sweeps `vse8.v v0..v31` from the regfile back to scratch
-  (`pb_v_data_sweep`, load=false); `read_v_from_scratch` lifts the bytes into
-  `hybrid_state_v1::vreg[]` (the drained handoff file; there is no QEMU2 ship step).
-
-Each sweep leads with `vsetvl` to e8/m8 (vl=8*vlenb), which also forces vstart=0;
-with LMUL=8 one `vle8.v`/`vse8.v` moves a group of 8 registers, so all 32 move in
-4 grouped ops in a single Program-Buffer execution. The scratch is packed at the
-RUNTIME vlenb stride (`stage_v_to_scratch` drops the wire-format
-`HYBRID_VLEN_BYTES_MAX` padding so each 8-register group is contiguous).
-
-V scalar CSR transport (vtype, vl, vstart, vxsat, vxrm, vcsr):
-- **Tier A** (Abstract Commands): vstart, vxsat, vxrm, vcsr, mstatus.VS
-- **Tier B** (Program Buffer): vtype + vl via `vsetvl x0, x5, x6` (direct CSR write to vtype sets vill; vl is read-only; only `vsetvl` restores both atomically)
-
-Restore order in `ResumeDriver::resume()` when `HYBRID_FLAG_V` is set:
-1. `mstatus.VS` (enables V in the hart)
-2. V-data reload sweep: `vsetvl` e8/m8 then `vle8.v v0..v31` from scratch in the
-   Program Buffer. Runs BEFORE the architectural V-CSR restore (whose `vsetvl`
-   overwrites the sweep's vtype/vl/vstart) and uses x5/x6/x7 as scratch.
-3. `vsetvl x0, x5, x6` in Program Buffer (stages `vl` in x5, `vtype` in x6 via abstract GPR writes first)
-4. `vstart` (AFTER vsetvl: vsetvl resets vstart to 0)
-5. `vxsat`, `vxrm`, `vcsr`
-6. GPR loop (overwrites the x5/x6/x7 scratch - safe now)
-
-`StateDrain::drain_with_passthrough()` issues the matching `vse8.v` dump sweep
-LAST, after every architectural read (GPRs/FPRs/V-CSRs/mcycle/minstret), so the
-sweep's clobbers and any counter increments cannot corrupt the drained state.

-### Test Fixtures
-
-All fixtures run on the unified `tests/e2e.sh` harness, which
-sets up an `/dev/shm`-backed shared mmap (128 MB) so memory survives
-the QEMU1 -> vsim handoff. Three fixture families:

-|----------|-------------------------------------------------------------|-------|
-| asm      | `handoff_roundtrip`, `rt_all_gprs`, `rt_csr_survival`, `rt_shared_mem` | no C runtime; don't strictly need shared mmap but use it anyway (~20 ms cost is negligible). |

-| vplat    | `vplat_hello`, `vplat_exit41`, `vplat_file`                 | smoke tests for the runtime's own features (exit code, file io). -
-The shared mmap is created with `mktemp -p /dev/shm` + `truncate`,
-then QEMU is launched with `-object memory-backend-file`.
-
-Fixture source lives in `tests/fixtures/`; the shared runtime sources live at the repo root in `runtime/`. V-using fixtures require `-march=rv64gcv`. Syscalls bottom out in MMIO devices both engines model (UART2 `0xf0300000`, SimControl/HTIF `0xe0080000` -- QEMU side is inline in `QEMU/hw/riscv/andes_ae350.c`), so a `printf` inside the ROI works on every engine (it just adds the real UART cycles to the figure); the old "Phase-2 no-syscall rule" survives only as a measurement-hygiene convention in cycle-measuring fixtures, and as a hard rule for user binaries that still link a semihosting libgloss. The ROI markers are HINT NOPs, so vplat binaries may carry them (`<andesim/ROI.h>`, installed to `build/runtime/include/`) and still run standalone on every engine; binaries you cannot edit delimit the ROI with PC symbols and `--trigger pc` instead.

-# andesim User Guide
-
-Audience: an engineer who wants to RUN programs on the Andes simulators
-through `./andesim` and measure cycle counts. This guide covers every
-user-facing option and feature.
-
-It assumes andesim and its engines are already installed and built
-(QEMU, the vsim engines, the plugin, the runtime, and the test ELFs are
-prebuilt). If something is missing, run `./andesim doctor` and hand the
-report to whoever owns your install; building is covered in `README.md`,
-not here.
-
----
-
-## 1. What andesim is
-
-andesim runs one RISC-V ELF on one of three models:
-
-| Model    | What runs                              | Speed          | You get                    |
-|----------|----------------------------------------|----------------|-----------------------------|
-| `fast`   | QEMU only (functional)                 | MHz-class      | program output, fast        |
-| `cycle`  | one cycle-accurate engine, from reset  | kHz-class      | program output + total cycles |
-| `hybrid` | QEMU fast-forwards, then the cycle engine measures one region you choose | fast until your region | program output + cycles of JUST your region |
-
-`hybrid` is the headline feature: QEMU races through boot and setup, then
-hands the complete architectural state and memory to the cycle-accurate
-engine (vsim, built from the real RTL), which runs only your
-region-of-interest (ROI). The cycle figure is the vsim `mcycle` delta
-across that window. You mark the window with a **trigger**: source-level
-markers or a pair of PCs (section 5.3).
-
-One run models ONE core. The cycle engine defines the hardware (ISA,
-VLEN, caches); in hybrid mode the QEMU leg automatically inherits that
-engine's ISA and VLEN so both legs execute the same architecture.
-

-
-## 2. Check your installation
-
-```sh
-./andesim doctor          # read-only health report
-./andesim list models     # the three models
-./andesim list engines    # every engine you can pass to --engine
-```
-
-`doctor` checks artifacts, toolchain, runtime, engines, and the shared-memory
-backing tiers, and prints WSL2 advice where relevant. A healthy install ends
-with `Summary: N PASS, 0 FAIL`.
-
-`list engines` shows what `--engine` accepts:
-
-```
-ENGINE                 TYPE  KIND            XLEN  VLEN  DLEN  ELEN
-qemu64                 qemu  functional      64    -     -     -
-qemu32                 qemu  functional      32    -     -     -
-vsim:ax45mpv_premium   vsim  cycle-accurate  64    512   512   32
-vsim:ax46mpv_advanced  vsim  cycle-accurate  64    512   512   32
-```
-
-`qemu64`/`qemu32` are the functional engines (`fast`); the `vsim:<cfg>`
-entries are the cycle-accurate engines (`cycle`, and the measuring leg of
-`hybrid`). `-` means the engine does not report that parameter.
-
-Run `./andesim run -h` any time for the compact flag list; this guide is
-the long version.

-## 3. First runs
-
-The install ships ready-made ELFs under `tests/fixtures/`; the examples
-below use them. Replace with your own ELF once you have one (section 4).
-
-### 3.1 fast -- functional, full speed
-
-```sh
-./andesim run --mode fast tests/fixtures/vplat_hello.elf
-```
-
-```
-hello from vplat
-```
-
-Output is the program's own output, verbatim (QEMU passthrough). The exit
-code of your program becomes the process exit code.
-
-### 3.2 cycle -- one engine, from reset, total cycles
-
-```sh
-./andesim run --mode cycle --engine vsim:ax45mpv_premium tests/fixtures/vplat_hello.elf
-```
-
-```
-hello from vplat
-[andesim] 4247 cycles
-```
-
-The engine's startup banner and verbose info log are filtered out so the
-result stands alone; real warnings/errors still pass through, and the
-program's exit code is propagated. The figure is the whole run from reset
--- boot, runtime init, everything.
-
-### 3.3 hybrid -- fast-forward, then measure your region
-
-`hybrid` needs a trigger that says where the measured window starts and
-ends. The fixture below already contains ROI markers, so `--trigger
-marker` works out of the box:
-
-```sh
-./andesim run --mode hybrid --trigger marker --engine vsim:ax45mpv_premium \
-  tests/fixtures/rt_c_hello.elf
-```
-
-```
-hello from QEMU1
-[andesim] 54 cycles
-```
-
-Reading the output:
-
-- `hello from QEMU1` is the program's own output from the fast leg.
-- `[andesim] 54 cycles` is the answer: your ROI took 54 cycles on
-  this engine. It is the vsim `mcycle` delta across the window (the same
-  line shape `cycle` mode prints, but here it covers JUST your ROI).
-- The run ends after the ROI. Code after your ROI never executes in a
-  hybrid run -- hybrid is a measuring tool, not a way to finish the program.
-- Want more detail? `--log-level 1` (section 5.10) adds the driver's
-  chatter: the resolved engine/VLEN/trigger banner and the shared-memory
-  line (`[andesim] mmap ...`, section 5.4).
-
-The first hybrid run of a given (engine, ELF) pair is a few seconds slower:
-andesim captures the engine's reset state once and caches it under
-`~/.cache/andesim/` so later runs can skip restoring registers that still
-hold reset values (typically ~4x faster on the vsim leg). The cache
-refreshes itself when the engine or the ELF changes.

-## 4. Prepare your own program
-
-### 4.1 Compile once, run on every engine
-
-Link against the andesim runtime and one ELF runs on `fast`, on `cycle`,
-and across a `hybrid` handoff -- no per-engine builds, no semihosting:
-
-```sh
-riscv64-unknown-elf-gcc -march=rv64gc -mabi=lp64d -O2 \
-  -B <andesim>/build/runtime -specs=andesim.specs your_prog.c -o your_prog.elf
-```
-
-- Use your Andes RISC-V GCC (the one `./andesim doctor` reports).
-- `-B` points gcc at the runtime artifacts; use the absolute path when
-  compiling outside the repo.
-- `-specs=andesim.specs` swaps in the runtime's `crt0.o`, links
-  `andesim.ld` (load base `0x00100000`), and pins the library order, so no
-  semihosting library can leak into the link.
-- Add `v` to `-march` (e.g. `rv64gcv`) for RVV code.
-
-For rv32 targets use the rv32 compiler and the rv32 runtime flavor:
-
-```sh
-riscv32-unknown-elf-gcc -march=rv32gc -mabi=ilp32d -O2 \
-  -B <andesim>/build/runtime/rv32 -specs=andesim.specs your_prog.c -o your_prog.elf
-```
-
-Custom build system (no gcc driver)? Link the pieces directly:
-
-```sh
-... -nostartfiles -nodefaultlibs -T build/runtime/andesim.ld \
-  build/runtime/crt0.o your_prog.o -L build/runtime \
-  -Wl,--start-group -landesim_runtime -lc -lgcc -Wl,--end-group
-```
-
-What the runtime gives your program, on every engine:
-
-| Channel          | Behavior                                                       |
-|------------------|----------------------------------------------------------------|
-| stdio (fd 0-2)   | `printf` etc. go to the simulator console (a modeled UART)     |
-| exit code        | `exit(n)` (n < 256) terminates the simulation; `n` becomes the simulator process exit code |
-| file io (fd > 2) | `open`/`read`/`write` pass through to host files, resolved against the engine's working directory |
-
-A `printf` inside a measured ROI works -- but it adds the real UART cycles
-to your figure. Keep measured kernels I/O-free when you want clean numbers.
-
-### 4.2 Mark your region (ROI markers)
-
-For `--trigger marker`, wrap the region you want to measure:
-
-```c
-#include <andesim/ROI.h>   /* shipped with the runtime; rides the -B flag */
-
-andesim_ROI_begin();
-my_kernel(a, b, c);
-andesim_ROI_end();
-```
-
-The markers are RISC-V HINT instructions (architectural NOPs), so a marker
-binary also runs unchanged on `fast`, on `cycle`, and on real silicon.
-Ship one binary; measure when you want.
-
-> **Measurement hygiene:** keep the kernel anchored inside the marker span
-> -- read its inputs and write its outputs through memory inside the span,
-> or wrap the kernel in a `__attribute__((noinline))` function called
-> between the markers. The markers pin memory I/O but not register-only
-> compute, so a kernel that carries live values in registers across the
-> boundary may be hoisted or sunk out of the measured window by the
-> compiler.
-
-### 4.3 Cannot edit the binary? Use PC boundaries
-
-`--trigger pc` needs no markers: you name the window with `--pc-start` and
-`--pc-end`, each a symbol name or a `0x` address (section 5.3). To find
-the hot region of an unknown binary first, run the profile command:
-
-```sh
-./andesim profile --min-iters 10 my_kernel.elf
-```
-
-It runs the binary fast (QEMU, configured like your engine) and reports
-the hottest loops (function, source line, PCs) with a ready `measure:`
-line -- a `--pc-start`/`--pc-end` pair you can paste straight into the
-hybrid command. See section 6 and `docs/profile.md` for the full flag
-reference.

-## 5. The `run` options, one by one
-
-Synopsis:
-
-```
-./andesim run --mode fast|cycle|hybrid [options] <ELF> [-- <engine args>]
-```
-
-`run` is the default command -- you may omit it. `./andesim --mode fast
-my.elf` and `./andesim my.elf --mode fast` both work; only the explicit
-commands (`profile`, `list`, `doctor`) are recognized by name.
-
-### 5.1 `--mode fast|cycle|hybrid` (required)
-
-Picks the model (section 1). Everything else keys off this choice.
-
-### 5.2 `--engine <id>`
-
-Picks the engine from `./andesim list engines`.
-
-- `fast`: optional. The driver auto-selects `qemu64` or `qemu32` to match
-  your ELF's width; an explicit `--engine qemu32|qemu64` overrides (with a
-  warning if it disagrees with the ELF).
-- `cycle` / `hybrid`: names the cycle-accurate engine. Optional only when
-  exactly one is installed; with several you must choose:
-
-  ```
-  andesim run --mode cycle: model cycle: multiple cycle-accurate engines;
-  select one with --engine (have: vsim:ax45mpv_premium, vsim:ax46mpv_advanced)
-  ```
-
-Width rules: `cycle`/`hybrid` reject an ELF whose width does not match the
-engine, up front:
-
-```
-andesim run --mode cycle: ELF is rv32 but engine 'vsim:ax45mpv_premium' is rv64
-  -- pick a matching engine or an rv64 ELF
-```
-
-Hybrid additionally requires an rv64 engine (the fast leg is rv64; an rv32
-engine cannot share architectural state with it and is rejected).
-
-VLEN: each vsim engine has a fixed VLEN (see `list engines`); in hybrid
-mode the QEMU leg inherits the engine's ISA and VLEN automatically, so
-both legs execute identical architecture. Supported VLEN range in hybrid:
-128 to 1024 bits. A standalone `fast` run defaults to the vector-capable
-`andes-ax46mpv` (rv64) / `andes-a46mpv` (rv32) CPU model; to pin an exact
-VLEN there, append a `-cpu` through the passthrough tail (the last `-cpu`
-wins):
-
-```sh
-./andesim run --mode fast app.elf -- -cpu andes-ax46mpv,vlen=256
-```
-
-### 5.3 `--trigger marker|pc` (+ `--pc-start`, `--pc-end`) -- hybrid only, required
-
-The ROI delimiter for `--mode hybrid`.
-
-**`--trigger marker`** (recommended when you can edit the source): the
-window is the span strictly between `andesim_ROI_begin()` and
-`andesim_ROI_end()` (section 4.2). The markers themselves are NOPs and
-cost nothing.
-
-**`--trigger pc`**: explicit boundaries, no source edits. Both flags are
-required; each accepts a symbol name or a `0x` hex address:
-
-```sh
-./andesim run --mode hybrid --trigger pc --engine vsim:ax45mpv_premium \
-  --pc-start vmatmul_kernel --pc-end 0x1002cc my.elf
-```
-
-Semantics you should know:
-
-- The instruction at `--pc-start` executes INSIDE the measured window (the
-  fast leg stops just before it; the cycle engine resumes at it -- no
-  instruction is lost across the handoff). `--pc-end` is where the window
-  closes.
-- Symbols are resolved from the ELF's own symbol table by the driver; no
-  toolchain is needed at run time. A name that is not defined fails with
-  `symbol '<x>' not defined in <elf>`; a bad literal fails with
-  `malformed address '<x>'`.
-- Both triggers are one-shot: the first hit of the start boundary opens the
-  window, the first hit of the end boundary closes it. For a function called
-  many times, the window is the FIRST call.
-- Start and end must resolve to different addresses; an equal pair is an
-  empty window and is rejected up front:
-  `--pc-start and --pc-end resolve to the same address 0x... (an empty ROI measures nothing)`.
-
-### 5.4 `--mem-size <spec>` -- guest memory
-
-`SPEC` accepts `256M`, `1.5G`, `2G`, or raw bytes. Per-model meaning:
-
-| Model    | Effect |
-|----------|--------|
-| `hybrid` | Your program RAM (default `128M`). Max `2G` minus 4 KiB: the driver reserves one page just above your RAM for the vector-register transport, so exactly `2G` is rejected (use `2047M`) and an ELF whose static image reaches into the reserved page is rejected with `raise --mem-size or shrink the image`. |
-| `fast`   | Forwarded as a plain QEMU `-m`. No 2G cap; QEMU validates the size itself. |
-| `cycle`  | Ignored (the engine always models its full DRAM window); the driver says so on stderr. |
-
-Where the hybrid shared memory lives: andesim allocates a file both legs
-map. It picks the first tier with enough free space (request + 256 MiB
-headroom); run with `--log-level 1` to see which:
-
-1. `/dev/shm` -- RAM-backed, fastest.
-2. `~/.cache/andesim` -- disk-backed fallback (honors `XDG_CACHE_HOME`).
-
-```
-[andesim] mmap 2.0 GiB at /home/u/.cache/andesim (free: 2.1 TiB) (fallback: /dev/shm too small (1.2 GiB free))
-```
-
-Set `HSIM_MMAP_DIR=/path` to pin one directory with NO fallback past it
-(the run fails with a hint if it cannot hold the request). Do not pin a
-tmpfs mount (`/tmp` on some distros) expecting a disk ceiling -- tmpfs is
-still RAM.
-
-### 5.5 `--print-memmap` -- which addresses may a hybrid workload touch?
-
-Prints the guest memory map for exactly the run you are about to do (same
-`--engine`/`--mem-size`; the ELF is optional and only adds a fit note),
-then exits without running anything. Hybrid only.
-
-```sh
-./andesim run --mode hybrid --print-memmap --engine vsim:ax45mpv_premium --mem-size 128M
-```
-
-```
-[andesim] hybrid memory map: engine=vsim:ax45mpv_premium mem-size=128M
-REGION           BASE         END          SIZE    TRANSPORT
-DRAM             0x0          0x7ffffff    128M    shared mmap; content survives the handoff
-V-scratch        0x8000000    0x8000fff    4K      reserved by the hybrid V transport; not program-usable
-ILM              0x0          0xffff       64K     sidecar .ilm; DRAM overlay while milmb.IEN=1
-DLM              0x200000     0x207fff     32K     sidecar .dlm; DRAM overlay while mdlmb.IEN=1
-HVM              0x90000000   0x9003ffff   256K    sidecar .hvm
-SimControl/HTIF  0xe0080000   0xe0080fff   4K      device; state does not cross the handoff
-UART2            0xf0300000   0xf03fffff   1M      device (console); state does not cross the handoff
-```
-
-How to read it:
-
-- END is the inclusive last byte.
-- DRAM tracks `--mem-size`; the V-scratch page above it belongs to andesim.
-- ILM/DLM/HVM rows appear only when the chosen engine has those memories
-  and can transport their content; the addresses are the engine's own.
-- Device state never crosses the handoff (each engine has its own UART and
-  SimControl instance); only RAM content does.
-- Anything NOT listed is unsupported in hybrid mode: it exists in one
-  engine only, so touching it inside the ROI gives engine-specific behavior.
-
-### 5.6 `--dry-run` -- preview without running
-
-Valid in every mode: prints the exact engine command line(s), fully
-resolved and shell-quoted, and runs nothing. `fast`/`cycle` print one
-command; `hybrid` prints both legs. Use it to see precisely what a run
-will execute, or to lift the command for your own scripting.
-
-```sh
-./andesim run --mode hybrid --trigger marker --engine vsim:ax45mpv_premium --dry-run my.elf
-# [andesim] dry-run: 2 command(s), not executed
-# # command 1/2: fast-leg [qemu64]
-# qemu-system-riscv64 ... -plugin .../libhybrid_handoff.so,outfile=...
-# # command 2/2: accurate-leg [vsim:ax45mpv_premium]
-# sim_ax45mpv_premium my.elf --resume-from-qemu ... --handoff-out ...
-```
-
-### 5.7 `--verify` -- cross-check a hybrid run against a QEMU oracle
-
-A hybrid run normally proves only that a cycle figure came out. `--verify`
-(hybrid only, default off) re-runs the same ELF on pure QEMU up to the ROI
-exit and compares the architectural state field by field against what the
-cycle engine drained:
-
-```
-[andesim] 46 cycles
-[state-diff] PASS: 109 fields match (counters and passthrough CSRs excluded)
-[verify] PASS: vsim drain matches the QEMU oracle
-```
-
-A mismatch lists each differing field and exits non-zero:
-
-```
-[state-diff] x10: ref=0x3d got=0x0
-[state-diff] FAIL: 1 mismatch(es) (115 fields compared)
-```
-
-What is compared: the PC, all GPRs, FPRs (when FP state is live), the
-vector registers and V CSRs (when V is live), the privilege level, and the
-M-mode CSRs that round-trip through the handoff. On an S-mode-capable
-engine (one whose `--describe` names them, e.g. `vsim:ax66_makatau`) the
-S/U trap CSRs `satp`, `medeleg`, and `mideleg` also round-trip and are
-compared. Deliberately excluded: `mcycle`/`minstret` (the engines count
-differently by design), `mip` (hardware-driven pending bits), and a few
-CSRs whose reset values legitimately differ between engines.
-
-Two costs: one extra QEMU run of the whole program (cheap), and a full
-register read-back over the Debug Module at the ROI exit (not cheap --
-without `--verify` the exit drain reads only the two counters). Expect a
-`--verify` run to take noticeably longer; the cycle figure itself is not
-affected.
-
-Related, printed on EVERY hybrid run (not just `--verify`): andesim tracks
-which config CSRs your program actually wrote during the fast leg and
-warns if any of them do not exist on the chosen cycle engine:
-
-```
-[andesim] warning: the program wrote CSRs engine vsim:<engine> does not
-implement: <names> (on this engine's silicon these writes would trap; the
-hybrid restore skipped them)
-```
-
-That means your program, on that engine's real silicon, would trap before
-the ROI -- pick an engine that implements those CSRs, or drop the writes.
-A clean run prints nothing.
-
-### 5.8 `--kanata <file>` (+ `--objdump <file>`) -- pipeline trace of the ROI
-
-Hybrid only (`--trigger marker|pc`). Writes a Kanata-format pipeline trace
-covering exactly the measured window -- engine boot and handoff overhead
-are filtered out. Open the file in
-[Konata](https://github.com/shioyadan/Konata) to see the pipeline.
-
-```sh
-./andesim run tests/fixtures/rt_c_v_matmul.elf \
-  --mode hybrid --trigger marker --engine vsim:ax45mpv_premium \
-  --kanata /tmp/roi.kanata
-```
-
-Add `--objdump <file>` (a text dump you generated once with
-`riscv64-unknown-elf-objdump -d my.elf > my.S`) and the trace embeds the
-disassembly next to each PC. `--objdump` requires `--kanata`.
-
-Marker-mode constraint: the ELF must contain exactly one exit marker. With
-more than one, the run errors out and tells you to use `--trigger pc` with
-an explicit `--pc-end` instead.
-
-### 5.9 `--gdb` (+ `--gdb-port <port>`) -- attach a debugger
-
-Pauses the simulation at startup so a debugger can attach. Not available
-in hybrid mode.
-
-**fast** -- opens QEMU's GDB stub (default port 1234) and waits:
-
-```sh
-./andesim run --mode fast --gdb my.elf
-# other terminal:
-gdb-multiarch -ex 'target remote :1234' my.elf
-```
-
-**cycle** -- resets and HALTS the hart, opens the engine's JTAG bitbang
-port (default 9104) in the background, then execs `$ICEMAN` -- your JTAG
-debug server -- in the foreground. Point GDB at the server's own gdb port
-(from your server config), not at 9104:
-
-```sh
-export ICEMAN=/path/to/jtag-debug-server

-

-pipeline.

-is emitted BEFORE the spawn, so even a hung run leaves the command in

-```

-## 6. The `profile` command -- find your ROI first
-
-When you do not yet know WHERE the hot region is, run `profile` before
-`run --mode hybrid`:
-
-```sh
-./andesim profile [--engine <id>] my_kernel.elf
-```
-
-It runs the whole ELF under QEMU with a loop-detector plugin
-(`libhotIterationLoop.so`) and prints a Markdown report of the hottest
-loops. Each loop block ends with a ready window:
-
-```
-measure:      --pc-start 0x10007c --pc-end 0x1000c2  (all of vadd_kernel: entry -> ret)
-```
-
-Paste that pair into `./andesim run --mode hybrid --trigger pc ...` to
-measure exactly that function on the cycle engine.

-the sole installed cycle-accurate engine) and launches QEMU with THAT

-fast leg gets. So the loop ranking reflects the ISA (including VLEN) of
-the engine you will measure on.

-report, `--no-optimize-rvv` also shows scalar loops (the default reports

-previews the QEMU command. Full reference: `docs/profile.md`.

-## 7. What a hybrid run does for you automatically
-
-You normally do not need this section to use andesim -- it explains the
-behaviors you will observe.
-
-**Two legs, one state.** The fast leg (QEMU) runs to your ROI start, then
-drains the complete architectural state -- GPRs, FPRs, vector registers,
-CSRs (including the Andes-specific blocks), privilege level -- into a
-state file. Program RAM is shared by construction (both legs map the same
-file), so memory needs no copy. The cycle engine restores the state
-through its Debug Module, runs your ROI, and drains the counters at the
-exit trigger. The cycle figure is the vsim `mcycle` delta.
-
-**Config that matters for timing rides along.** Cache-enable state (L1
-`mcache_ctl`, and the L2 controller's config window on engines that have
-an L2) is restored before the ROI, so a program that enabled caches during
-boot measures WITH caches on -- not at the engine's reset default.
-
-**Only what your program wrote is restored.** andesim records which config
-CSRs the program actually wrote during the fast leg and restores only
-those; an untouched CSR keeps the engine's own reset value, exactly like
-that engine's real silicon. If the program wrote a CSR the engine does not
-implement, you get the warning shown in section 5.7.
-
-**Local memories travel too.** On engines with ILM/DLM (tightly-coupled
-memories) or HVM (high-bandwidth vector memory), their content is drained
-from the fast leg and loaded into the cycle engine before resume, so a
-program that stages code or data there before the ROI resumes with it in
-place. (A program using ILM/DLM must enable them itself via
-`milmb`/`mdlmb`, as real TCM firmware does; that write is restored
-automatically.) `--print-memmap` shows whether your engine has these
-regions.
-
-**First-run baseline capture.** Restoring a register over the Debug Module
-costs hundreds of simulated cycles, and most state still holds reset
-values. The first hybrid run of a given (engine build, ELF) pair captures
-the engine's reset state once and caches it under `~/.cache/andesim/`
-(honors `XDG_CACHE_HOME`); later runs skip the no-op restores, typically
-cutting the vsim leg ~4x. The cache invalidates itself when the engine or
-ELF changes; delete the directory to force a fresh capture. This never
-changes results -- a restore is skipped only when the value is already
-there.
-
-**The ROI envelope (limits).** The measured window is assumed bare-metal,
-single-hart, trap-free, interrupt-free, paging-off, and single-privilege.
-The S/U trap CSRs `satp`, `medeleg`, and `mideleg` are transported on
-S-mode-capable engines (so an in-ROI read sees your values); other S-mode
-CSRs (`sstatus`, `sepc`, ...) are not transported yet. The privilege level
-itself IS carried: an S/U-mode handoff also mirrors the PMP configuration
-and requires an S/U-capable engine -- on an M-mode-only engine the resume
-aborts with a clear pick-another-engine error. A workload that traps,
-takes an interrupt, or switches privilege inside the ROI is outside the
-contract. And because there is no hand-back leg, nothing after the ROI
-executes.

-## 9. Troubleshooting
-
-| Symptom | Meaning / fix |
-|---------|----------------|
-| `multiple cycle-accurate engines; select one with --engine (have: ...)` | More than one engine is installed. Add `--engine <id>` from `list engines`. |
-| `ELF is rv32 but engine '...' is rv64 -- pick a matching engine or an rv64 ELF` | Width mismatch caught up front. Rebuild the ELF for the engine's width or pick the other engine. |
-| `--trigger marker\|pc is required (the ROI delimiter; ...)` | Hybrid always needs the ROI delimiter: `--trigger marker` (markers in source) or `--trigger pc --pc-start S --pc-end E`. |
-| The run never reaches the ROI / hangs until timeout | The start trigger never fired: the binary has no markers (marker mode), or `--pc-start` is never executed. Check with `--trigger pc` on a PC you know retires, or run `./andesim profile` to find real hot PCs. |
-| `symbol '<x>' not defined in <elf>` / `malformed address '<x>'` | `--pc-start`/`--pc-end` must be a defined symbol or a valid `0x` literal. |
-| `--pc-start and --pc-end resolve to the same address ... (an empty ROI measures nothing)` | Pick two distinct boundaries; equal ones would measure nothing. |
-| `--mem-size ...` rejected, or `raise --mem-size or shrink the image` | Hybrid caps at `2G` minus 4 KiB (use `2047M`), and the ELF's static image must fit below the reserved V-scratch page. |
-| The mmap chose a disk directory (`[andesim] mmap ...` at `--log-level 1`), or `HSIM_MMAP_DIR` run fails | `/dev/shm` was too small for the request. Either accept the disk tier, free RAM, or pin a big non-tmpfs directory via `HSIM_MMAP_DIR`. |
-| `warning: the program wrote CSRs engine ... does not implement: ...` | The figure may not represent this program on this engine (on silicon those writes would trap). Choose an engine implementing those CSRs, or drop the writes. |
-| `multiple ... markers in ELF -- use --mode hybrid --trigger pc ...` (with `--kanata`) | Kanata needs a unique exit; switch to `--trigger pc` and name the exit with `--pc-end`. |
-| `hybrid` rejects `-- <args>` | By design: hybrid owns both legs' command lines. Use the dedicated flags instead. |
-| Missing artifact / engine not discovered | Run `./andesim doctor`; it names exactly what is missing and where it looked. Setup/build is covered in `README.md`. |
-| A hybrid leg failed and you want to report or debug it | The run printed `[andesim] repro: kept run artifacts at <dir>` -- that directory holds the evidence and `manifest.txt` has each leg's exact command (newest 20 kept). Re-run with `--log-file run.log` (and `--log-level 1` for live engine logs) for the full picture. |

-# Hybrid State Transport: CSR Problems and MMIO Problems
-
-## Background (read this first)
-
-A hybrid run uses TWO simulators for ONE program:
-
-```
-  QEMU (fast, no timing)          vsim (slow, cycle-accurate)
-  boot + setup code       ---->   the measured region (ROI)
-                        "handoff"
-```
-
-At the handoff we must make vsim's CPU look EXACTLY like QEMU's CPU at
-that moment. The copy has two steps:
-
-- **drain**: read all state out of QEMU into a file (`hybrid_state_v1`).
-- **restore**: write that file into the vsim hart through the Debug
-  Module, then let it run.
-
-Two kinds of state travel, and their problems are different enough to
-list separately:
-
-- **CSR**: a register inside the CPU (mstatus, mcache_ctl, ...),
-  accessed by the `csrr`/`csrw` instructions.
-- **MMIO**: a register inside a device, reached by a memory address
-  (the L2 cache controller at 0xE0500000, ...), accessed by ordinary
-  load/store instructions.
-
-**(*) One global caveat.** Every vsim-side fix below is committed as
-SOURCE, but the prebuilt `sim_*` binaries were built before ABI v5/v6.
-They reject the new state files (version check) until the Docker
-rebuild (`build_vsim.sh`) picks up the new pin. So items marked (*) are
-"solved in code, verified by unit tests, pending in the shipped
-binaries"; the full e2e revalidation is queued behind that rebuild.
-
----
-
-# Part 1: CSR problems
-
-## C1. Untouched CSRs: defaults differ, and the file cannot tell you who wrote what
-
-**The harm.** A CSR the program never writes just keeps its power-on
-("reset") value. QEMU's reset value and the engine RTL's reset value
-are not always the same. The drain reads QEMU's default out; restore
-then overwrites the engine's CORRECT default with QEMU's wrong one --
-the ROI runs with a value real silicon of that engine would never hold.
-
-Example: `mnvec` -- QEMU resets it to 0; the Andes RTL resets it to the
-hart's reset vector. Seen live as a false `--verify` failure.
-
-(How engine reset values are KNOWN at all: only by measurement -- the
-`--probe` halts the freshly-reset hart and reads every CSR, into each
-engine's `csr_manifest.csv`. Never trust hearsay: `msp_bound` was long
-quoted as "RTL resets 0", and the probe showed the HSP-capable ax46
-also resets all-ones, same as QEMU.)
-
-**Why the obvious fix does not work.** The obvious fix is "do not
-restore registers the program never wrote". But the drained file
-carries only VALUES, not write history. `mcache_ctl = 0` can mean
-"program disabled the caches on purpose" (must restore!) or "program
-never touched it and 0 is QEMU's default" (must NOT restore!). Looking
-at the file, the consumer cannot tell these apart -- so the fix cannot
-live on the consumer side.
-
-**The fix (v6 write-mask): record the fact at the source.** The QEMU
-plugin decodes every CSR-write instruction at translation time
-(`csrrw`/`csrrwi` always write; `csrrs/c` only when rs1 != x0;
-`csrrsi/ci` only when uimm != 0) and sets one bit per governed CSR:
-"the guest wrote this". Restore and `--verify` act only on set bits;
-everything else keeps the engine's own default. Reset divergence then
-cannot matter, for any current or future engine, with zero per-engine
-data inside QEMU.
-
-**Status: SOLVED (*).** Slot map + decoder:
-`include/hybrid/write_mask.h` (ABI v6). Tracking:
-`qemu_plugin/hybrid_handoff.c`. Restore gate `wm_live`: vsim
-`src/hybrid/resume_driver.hpp`. Verify gate: `driver/state_diff.cpp`.
-Proven by `write_mask.test.cpp` (decoder vs golden encodings),
-`test_plugin_write_mask.sh` (real QEMU: written bits set, a pure read
-stays clear, `ucode` always set), recording-bus and state_diff unit
-tests. Cost is near zero: only genuine CSR-write instructions get a
-callback, and those run a handful of times at boot. The
-historically-hit CSRs (`mnvec`, `msp_bound`, `milmb`...) additionally
-stay on the verify exclusion list as a belt, until one e2e pass on a
-rebuilt engine confirms the mask makes those entries redundant.
-
-## C2. This engine may not implement the CSR at all
-
-**What happens.** Engines differ in which CSRs even exist: premium has
-no HSP (`msp_bound` absent), ax46 has it; a future engine adds CLIC.
-One QEMU must serve them all, so nothing engine-specific may be
-hardcoded into QEMU, and the restore must not assume a CSR exists.
-
-**Example.** Restoring `msp_bound` on premium: the CSR is not there.
-
-**Status: SOLVED, one piece in flight.** (a) Tolerant writes: an
-absent CSR raises a small error flag (cmderr) that is cleared and
-skipped (`resume_driver.hpp write_csr_tolerant`). (b) Capability gates
-from the per-engine manifest
-(`tests/engines/<engine>/csr_manifest.csv`, generated by
-`gen_manifest.py` from the `--probe`: "measure, don't model");
-`andes_caps.hpp` gates restore/drain/verify. QEMU keeps only family
-constants (`-cpu andes-ax66`, `vlen=...` -- see `scripts/run_e2e.sh`).
-In flight: the probe function and the manifest-driven runtime caps
-(`--transport-csrs`) currently live as uncommitted work in the vsim
-tree (`simulator.hpp`/`main.cpp`). (Mirror on the MMIO side: M2 --
-there the wrong access FAULTS instead of being forgiven.)
-
-**Known gap (opened by the write-mask).** Since restore now only
-touches CSRs the program actually WROTE, "mask bit set AND engine
-lacks the CSR" is a REAL signal: on this engine's silicon that `csrw`
-would trap at boot and the program would never reach the ROI. Today
-the caps gate skips such a CSR silently (it short-circuits before the
-tolerant write, so not even cmderr fires) -- the incompatibility is
-hidden. Planned fix: the driver diffs the drained write-mask against
-the engine manifest before spawning vsim and WARNS loudly (naming the
-CSRs and stating that real silicon would trap), with a strict flag to
-turn the warning into an error. Abort-by-default is reserved for
-provable semantic breakage (the `dcsr.prv` precedent, C3): severity
-here is workload-dependent, and cross-engine comparison runs may
-knowingly accept the mismatch.
-
-## C3. The hardware may silently refuse the write (WARL)
-
-**What happens.** A RISC-V field may accept only values it supports
-("write any, read legal"). You write X, the hardware keeps Y. The Debug
-Module reports success, so restore "worked" but the value is not there.
-
-**Examples.** `dcsr.prv` on an M-only engine is pinned to 3: restoring
-a U-mode state does not take, and the ROI would run in the wrong
-privilege. `mnvec` is held at the reset vector; a restored 0 is
-discarded.
-
-**Status: SOLVED.** For the case that changes semantics, restore
-writes THEN reads back: a `dcsr.prv` mismatch aborts with a
-"pick an S/U-capable engine" error (`resume_driver.hpp`, L6). Cosmetic
-WARL cases are on the verify exclusion list (`state_diff.cpp`).
-
-## C4. Some CSR values change by themselves
-
-**What happens.** Counters and pending bits are driven by hardware,
-not the program. QEMU advances by instructions, vsim by cycles, so
-these can NEVER match -- even when the transport is perfect. Comparing
-them would fail every run with a false alarm.
-
-**Examples.** `mip` timer-pending bit, `mcycle`/`minstret`,
-`mhpmcounter3-6`.
-
-**Status: SOLVED.** `--verify` skips them (`state_diff.cpp`;
-unit-tested). Physics, not a bug. (Mirror: M4.)
-
-## C5. Action CSRs must not be transported at all
-
-**What happens.** Some CSRs are commands, not storage: writing them
-performs an operation. Restoring a drained command value would re-run
-the operation at ROI entry.
-
-**Example.** `mcctlcommand` (0x7CC) issues an L1 cache operation on
-write.
-
-**Status: SOLVED by design.** The transported list
-(`HYBRID_M_EXT_CSR_LIST`, `include/hybrid/state_abi.h`) contains only
-registers that are plain state -- 0x7CB `mcctlbeginaddr` and 0x7CD
-`mcctldata` are in; 0x7CC is deliberately absent. (Mirror: M3.)
-
-## C6. Each CSR has its own legal write method
-
-**What happens.** Not every CSR can be written directly, and the order
-of writes matters.
-
-**Examples.** `vl`/`vtype` cannot be written by `csrw` at all -- only
-the `vsetvl` instruction sets them, and `vsetvl` also clears `vstart`,
-so `vstart` must be restored AFTER it. A batched restore script dies
-halfway if one CSR faults, leaving the hart half-restored.
-
-**Status: SOLVED.** Tier B: `vl`/`vtype` restore via a staged `vsetvl`
-in the Program Buffer, `vstart` written after it
-(`resume_driver.hpp`; ordering documented in CLAUDE.md). CSRs restore
-one abstract command at a time; the batched restore sweep was removed
-on purpose (vsim commit "remove legacy PB CSR-sweep restore path").
-(Mirror: M5.)
-
-## C7. The wrong branch already ran before the handoff
-
-**What happens.** Transport copies state AT the boundary, but the boot
-code already RAN on QEMU. If it READ a config CSR and QEMU's config
-differs from the engine's, it took the wrong branch -- and no state
-copy can undo a branch that already executed.
-
-**Step-by-step example.**
-1. BSP reads `mmsc_cfg.PPMA` ("do I have programmable PMA?").
-2. The engine has PPMA=1; QEMU's CPU model says 0.
-3. The boot code SKIPS the PMA setup -- on QEMU, where it ran.
-4. vsim faithfully restores a state with unprogrammed PMA. The ROI
-   runs with memory attributes the real chip would never have.
-
-**Status: PARTIAL, by policy.** The mechanism exists and is used at
-family level: the driver/harness pairs `-cpu` and properties per engine
-(`scripts/run_e2e.sh`: `QEMU_CPU=andes-ax66,vlen=128`; the plugin tests
-use `andes-ax45mpv,vlen=512`). There is NO general per-config-bit
-coverage -- by design we add a QEMU property only when a real workload
-trips on a specific bit. No in-tree workload does today. (Mirror: M6.)
-

-# Part 2: MMIO problems
-
-## M1. The device model wakes up with the wrong values
-
-**What happens.** QEMU models the L2C register block as plain RAM,
-which starts as all zeros. The real device has spec-defined reset
-values. A program that trusts the hardware default never writes the
-register, so the drain reads QEMU's zero -- and restore would push that
-zero into a real device model. (This is the MMIO version of C1's harm.)
-
-**Step-by-step example (L2C CEN, the case we hit).**
-1. Real chip: after reset, L2C Control bit CEN = 1 (L2 cache ON).
-2. QEMU's RAM stub reads 0.
-3. The program relies on the default and never writes it.
-4. Drain reads CEN=0; restore writes CEN=0 into vsim.
-5. The ROI runs with L2 OFF: cycle count several times too big, and
-   no error is printed anywhere.
-
-**Status: SOLVED for the register that matters.** QEMU seeds the
-Control register's spec reset (CEN=1) at machine init
-(`hw/riscv/andes_ae350.c`, commit 86d433001e); proven by
-`test_plugin_l2c_reset_default.sh` (a guest that never writes 0x0008
-still drains CEN=1). Safe to hardcode because CEN=1 is an IP-spec
-constant, not an engine choice -- and once the defaults agree, C1's
-"who wrote it" trap is harmless for this register: both readings give
-the same, correct value. Other L2C registers are NOT seeded -- see M6.
-
-## M2. Restoring into an absent device FAULTS
-
-**What happens.** MMIO restore is a store instruction executed by the
-halted hart (through the Program Buffer). If this engine was built
-WITHOUT the device, there is nothing at that address: the store is a
-bus error, the Program Buffer faults, and the whole resume aborts.
-Unlike a CSR (C2), there is no "tolerant" mode for memory.
-
-**Example.** Every current engine is built `NDS_L2C_CACHE_SIZE_KB=0`.
-A `sw` to 0xE0500008 on them does not get ignored -- it faults.
-
-**Status: SOLVED (*).** Hard presence gate: `Simulator::l2c_present()`
-reads the engine's own build config (`_NDS_L2C_CACHE_SIZE_KB > 0`) and
-`ResumeDriver::restore_l2c` / `StateDrain::drain_l2c` issue nothing
-when absent (vsim `resume_driver.hpp`/`state_drain.hpp`/
-`simulator.hpp`). Unit-tested both ways (flag clear / device absent).
-
-## M3. Some device registers are buttons, not storage
-
-**What happens.** Writing certain MMIO registers triggers an action or
-destroys state, so "write the drained value back" is wrong for them.
-
-**Examples.** L2C CCTL Command register: writing 0x12 STARTS a full L2
-flush -- restoring it would run a cache flush inside the measured
-window. W1C error bits: writing 1 CLEARS them. The Configuration
-register is read-only anyway.
-
-**Status: SOLVED (*).** The plugin captures the WHOLE 0x0000..0x0527
-window into the file; `restore_l2c` writes back only the whitelist --
-Control (0x0008), HPM Control (0x0010), Way Allocation Masks
-(0x0300..) -- never CCTL/W1C/RO registers (`resume_driver.hpp`; offsets
-defined in `include/hybrid/state_abi.h`). (Mirror: C5.)
-
-## M4. Some device status changes by itself
-
-**What happens.** Status bits driven by the device, not the program,
-cannot match between a functional model and a cycle model.
-
-**Example.** L2C `INITSTATUS[14]`: a real L2C drives it while its TAG
-RAMs initialize; QEMU's RAM stub never changes it.
-
-**Status: SOLVED.** `state_diff.cpp` compares `l2c.ctrl` with bit 14
-masked out; unit-tested. (Mirror: C4.)
-
-## M5. The device dictates the access width
-
-**What happens.** Device buses have rules; breaking them is
-UNPREDICTABLE per the spec.
-
-**Example.** DS220 11.8.3: L2C registers must be accessed with single
-transfers SMALLER than 8 bytes. So the transport must use `sw`/`lwu`
-(32-bit), never `sd`/`ld` (64-bit).
-
-**Status: SOLVED (*).** `encode_sw`/`encode_lwu` word accesses in the
-Program Buffer (vsim `src/hybrid/program_buffer.hpp`), `lwu`
-(zero-extend) so a 32-bit read does not sign-pollute the 64-bit file
-slot. Golden-hex unit tests from `riscv64-elf-as`. (Mirror: C6.)
-
-## M6. The stub lies to programs that READ it
-
-**What happens.** Boot code may read device config and branch on it.
-QEMU's RAM stub returns whatever is in RAM (mostly zeros), not what the
-real device would report -- and the wrong branch has already run by the
-time we hand off.
-
-**Example.** Reading the L2C Configuration register's SIZE field
-returns 0 from the stub.
-
-**Status: OPEN (accepted for now).** Only CEN is seeded (M1). SIZE
-cannot be fixed the same way: it is engine-specific (depends on the
-engine's L2 size), and QEMU must stay engine-agnostic -- so the fix,
-when a real workload needs it, is a QEMU property the driver sets per
-engine (like `vlen=512`), or a real L2C device model. Today no in-tree
-code reads it: the vplat runtime checks `mmsc_cfg` bit 46 (CPU model,
-truthful) and CEN (seeded, truthful). (Mirror: C7.)
-
-## M7. Devices that exist on only one side
-
-**What happens.** QEMU models the whole AE350 platform (PLIC, PIT,
-WDT, RTC, GPIO, DMAC...). vsim models only a handful (its
-`platform/memory_map.h`): RAM, local memories (ILM/DLM), UART1/2,
-SimControl, the debug module, SMU, the AIA interrupt files -- no PLIC,
-no timers, no GPIO. ROI code touching a QEMU-only device runs fine in
-the functional phase and BUS-FAULTS in the cycle phase. Their internal
-state also cannot be transported -- it lives inside each simulator.
-
-**Example.** Reading the PIT timer inside the ROI.
-
-**Status: CONTRACT (no code enforcement).** Documented ROI rule: do
-not touch single-sided devices; inside the ROI use only dual-modeled
-ones (UART2 printf, SimControl exit -- both engines model them). If
-enforcement is ever wanted, the plugin could warn on ROI-window
-accesses outside the dual-modeled ranges -- not planned.
-

-# andesim profile - hot inner-loop detector
-
-Finds the hottest loops in a baremetal RISC-V ELF by observing backward
-translation-block transitions in QEMU. For each detected loop you get the
-loop header PC, the backward-branch PC, the iteration count, and a ready
-`measure: --pc-start .. --pc-end ..` window you can paste into a hybrid
-run. With DWARF, you also get the source `file:line`. With objdump
-present, you get RVV-only filtering and per-loop disassembly context.
-
-Two parts ship together:
-
-- `qemu_plugin/hotIterationLoop.c` - QEMU TCG plugin
-  (`libhotIterationLoop.so`) that records edges.
-- `andesim profile` - the driver command that picks the engine, launches
-  QEMU with the plugin, and formats the report.
-
-## Usage
-
-```
-./andesim profile [--engine <id>] [options] <elf> [-- <extra qemu args>]
-```
-
-profile is engine-synced, exactly like hybrid: it picks a cycle-accurate
-engine (`--engine <id>`, or the sole installed one) and derives the QEMU
-launch from it -- the `-cpu` model from the engine's `--print-qemu-config`
-probe, `vlen` from its `--describe`, and the probe's config staged as
-`-readconfig`. So the profile sees the same ISA the engine will measure:
-a different `vlen` changes `vsetvl` trip counts, which changes the loop
-ranking itself.
-
-If the engine does not answer `--print-qemu-config`, profile warns and
-falls back to the family-default `-cpu` (the report may then not match
-the engine's ISA).
-

-
-| Flag                | Default   | Description                                                    |
-|---------------------|-----------|----------------------------------------------------------------|

-| `--min-iters <N>`   | 1         | Drop loops with fewer than N iterations (hot-loop threshold).  |

-make -C qemu_plugin

-## How it detects a loop
-
-For every translated block, the plugin remembers the PC of its last
-instruction. When the next-executed block starts at a PC `<=` that
-remembered PC, the transition is a backward edge - i.e. a loop iteration.
-The pair `(header_pc, tail_pc)` is the key; the count is the number of
-iterations.
-
-This catches every loop a real backward branch closes (for/while/do-while,
-goto, manually unrolled tails, etc.) without needing to model branch
-semantics.
-
-Caveat: each iteration counted is one *taken* backward branch. A loop
-that runs N times has N-1 taken backward branches plus one fall-through
-on exit, so the reported count is N-1 per call to the enclosing function.
-
-## Output modes
-
-Three output modes, in order of layered post-processing:
-
-1. `--llm` (default on) - Markdown report tuned for LLM consumption.
-2. `--no-llm` - plain human-readable table.
-3. `--raw` - unformatted plugin output (overrides the above).
-
-### LLM report (default)
-
-The command emits a single Markdown document structured so an LLM (or a
-reader skimming top-down) can answer "what is the hottest loop?" from the
-first paragraph, then drill down via stable IDs.
-
-Layout:
-
-- Header block: `target`, `total_iters`, `reported_loops`, `min_iters`,
-  `rvv_filter`.
-- `## TL;DR` paragraph naming the hottest loop, its function and source
-  line, percentage of total iterations, RVV vs scalar (with the top-K
-  unique vector mnemonics seen), and nesting status.
-- One `### L<N>` fact-sheet per reported loop (sorted by iters desc):
-  - `iters`.
-  - `function` (`fn+0xoff -> fn+0xoff` at the loop's header and tail).
-  - `measure` - a ready `--pc-start 0x<entry> --pc-end 0x<ret>` pair
-    covering the loop's whole enclosing function (entry -> ret). Paste it
-    straight into `./andesim run --mode hybrid --trigger pc ...`.
-  - `source` (`file:line` or `file:line -> file:line` if the header and
-    tail map to different lines).
-  - `code` - inline best-effort source snippet read from the path stored
-    in DWARF.
-  - `rvv` summary plus `rvv_insns:` listing (capped at 8) with each
-    `0xpc  mnemonic operands`.
-  - `parent` / `children` - stable IDs of containing / contained loops.
-    Inferred from PC-range containment, so this captures only
-    same-function nesting.
-  - `calls` - direct callees inside the loop body (`jal`/`jalr` with a
-    statically known target via the `<name>` annotation). Indirect calls
-    show as `(indirect)`.
-
-The TL;DR is templated from the same data fields the per-loop blocks use;
-no LLM call is made by the command itself.
-
-Limitations:
-
-- Same-function nesting only. A caller's hot loop that calls a callee
-  containing its own hot loop will show as two unrelated loops; follow
-  `calls:` to bridge.

-  absolute path stored in DWARF. Cross-compiled or relocated builds may
-  fall back to just `file:line`.
-- The RVV filter is mnemonic-based: any insn whose mnemonic begins with
-  `v<alpha>` (e.g. `vsetvli`, `vle32.v`, `vadd.vv`, `vmul.vv`). Standard
-  scalar RISC-V has no such mnemonic, so this is exact in practice.
-

-Columns:

-## 0. What "switching mode" means
-
-The hybrid simulator runs a program across two phases:
-
-```
-   QEMU1  --(state file + shared mmap)-->  vsim
-   (fast)                                 (cycle accurate)
-```
-
-A "switching mode" is the RULE that decides WHEN QEMU1 drains its
-architectural state and hands the region of interest to vsim. vsim runs
-that region cycle-accurately, then drains the final state. You pick
-the rule with plugin args and vsim CLI flags; the fixture binary does not
-have to change between modes.
-
-> **Two ways to invoke, one canonical.** `./andesim run` is the driver -
-> the supported way to run a workload, and what the examples below lead
-> with. `tests/e2e.sh` is the regression harness that wraps the same legs
-> behind `FIXTURE=... TRIGGER_MODE=... bash tests/e2e.sh`; it adds test-only
-> assertions (`CHECK_MCYCLE_MONOTONIC`, `EXPECT_RC`, ...) and is shown only
-> where those diagnostics are the point. When in doubt, use `./andesim run`.
-
-The repo ships **2 modes**, both profiling a kernel.
-
-### Quick map
-
-| # | Mode | Profiles | Switch boundary | Cycle figure it yields |
-|---|------|----------|-----------------|------------------------|
-| 1 | marker | a kernel | `slti x0,x0,0x5A0` (enter) / `slti x0,x0,0x5A1` (exit) | kernel cycles |
-| 2 | PC | a kernel | a PC / symbol address (no source edit) | kernel cycles |
-
-- **Kernel modes (marker, PC)** measure ONE region you choose.
-
-(Migration: the old M1-M8 list collapses to these 2. Old M8 - the QEMU2
-semihosting exit - was removed with the QEMU2 phase, so every run now ends
-at the vsim drain.)
-
-### Where the cycle figure comes from
-
-Every mode reads the same counter: `mcycle`, a little-endian `uint64` at
-byte offset **624** in the state file (`include/hybrid/state_abi.h`). vsim
-restores `mcycle` from QEMU1's drained value, then the RTL counts real
-clock cycles, so the measured cycles are always a subtraction:
-
-```
-cycles = mcycle(vsim drain) - mcycle(QEMU1 drain)
-```
-
-The QEMU baseline cancels; only vsim's cycle-accurate delta survives. That
-is why QEMU being functional-only (not cycle-accurate) does not taint the
-number. marker/pc report this delta directly as the kernel cycles.

-## 2. marker mode - the default (profiles a kernel)
-
-### What it does
-
-QEMU1's plugin pattern-matches the encoding `slti x0, x0, 0x5A0` at retire
-time. On hit it drains state to `outfile` and exits 200. vsim does the
-same on `slti x0, x0, 0x5A1`. The markers are RISC-V HINT NOPs (rd=x0), safe on every
-core, so the fixture binary embeds these two `slti` instructions at the
-kernel boundaries. vsim's drain at the `slti x0, x0, 0x5A1` marker is the
-natural tail of the run.
-
-### Inputs
-
-- Fixture ELF with `slti x0, x0, 0x5A0` and `slti x0, x0, 0x5A1` in its source.
-  Every C-level fixture (rt_c_v_matmul, rt_c_v_regs, rt_c_matmul, etc.) has these.
-
-### Cycle figure
-
-Kernel cycles = the vsim `mcycle` delta over the region between the two
-markers. Run with `CHECK_MCYCLE_MONOTONIC=1` and the harness prints
-`mcycle` at both ends:

-```sh

-  bash tests/e2e.sh

-kernel cycle count is `vsim - qemu1` (the GEMM kernel is ~22808 cycles).

-## 3. PC mode - same kernel, no source edit
-
-### What it does
-
-Same round-trip as marker mode, but the trigger is a PC value, not an opcode
-match. The harness resolves each boundary - taken from the required
-`--pc-start` / `--pc-end` args (env-var form: `ROI_START` / `ROI_END`) -
-to an address (a `0x` value is used verbatim; a name is looked up with
-`nm`, see `tests/lib/roi.sh`), then passes:
-
-- `enter_pc=0x<addr>` to the QEMU plugin (QEMU1 drains there)
-- `--hybrid-exit-pc 0x<addr>` to vsim (vsim drains there)
-
-marker-mode matchers are bypassed; the marker instructions become
-inert. This proves you can hand off WITHOUT modifying the source: point the
-boundaries at any function or address the binary already has.
-
-### Inputs
-
-- Same fixture as marker mode (`rt_c_v_matmul`). Both PC boundaries are
-  **always explicit** -- pass `--pc-start S --pc-end E` (each a symbol
-  name or `0x` address). There is no implicit fallback to planted
-  `_hybrid_*_pc` markers.
-
-### Cycle figure
-
-Identical to marker mode: kernel cycles = vsim `mcycle` - QEMU1 `mcycle`.
-The boundaries differ, the measurement does not.
-

-## 6. Switching-mode decision flow

-```

-  binary is yours to edit

-## 7. Common failure signatures
-
-| Symptom                                                 | Likely cause                                                        |
-|---------------------------------------------------------|---------------------------------------------------------------------|
-| `SKIP: ... not built`                                   | `source ./setup.sh` not run, or partial build                       |
-| `QEMU 1 expected exit 200, got 0`                       | Trigger never fired (wrong mode, wrong PC target)      |
-| `QEMU 1 expected exit 200, got 124`                     | Plugin hung -> `timeout` killed it; check the PC target     |
-| `cannot resolve ROI start/end '<x>'`                    | PC-mode boundary `<x>` is neither a `0x` address nor a defined symbol; fix `--pc-start`/`--pc-end` (or `ROI_START`/`ROI_END`), or use marker mode |
-| `mcycle not strictly increasing across vsim`            | vsim measured zero cycles; check the kernel/window actually ran     |
-| Whole suite times out under scripts/run_e2e.sh          | `JOBS` too high; set `JOBS=8`                                        |
